# 남이 만든 다지 파지 모델 조사 — 가져다 쓸 수 있나

작성 2026-09-18.

> ⚠️ **조사 문서다. 계약을 바꾸지 않는다.** 관찰·행동 계약의 정본은
> [`RL_POLICY_REDESIGN.md`](RL_POLICY_REDESIGN.md), 파지 직전 자세 계획의 정본은
> [`FESTA_PREGRASP_PLAN.md`](FESTA_PREGRASP_PLAN.md) 이다.
>
> ⚠️ **아무것도 실행하지 않았다.** 전부 공개된 파일을 내려받아 읽고 확인한 것이다.
> "확인함" 은 *파일에서 읽었다* 는 뜻이지 *돌려 봤다* 는 뜻이 아니다.

**한 줄 결론**: 학습된 가중치는 **하나도 쓸 수 없다**. 대신 **코드 구조와 주고받는 값의
규약은 거의 그대로 가져올 값어치가 있다**. D(R,O) Grasp 는 새 손마다 재학습이 필요해
우리가 이미 하고 있는 일([`FESTA_PREGRASP_PLAN.md`](FESTA_PREGRASP_PLAN.md) §3)보다
싸지 않다.

## 0. 무엇을 조사했나

사용자가 지목한 후보 네 가지다.

| 후보 | 무엇 | 어디 |
|---|---|---|
| `Kaz55/act-newblue-gs0-ac60` | UR5e + DG-5F, 카메라 2대, ACT 방식 | Hugging Face |
| `Kaz55/act-nutv4-ac60` | 같은 구성 | Hugging Face |

**Kaz55 는 우리와 거의 같은 조합(UR 팔 + Tesollo DG-5F 오른손)으로 실제 작업을 한
사람이다.** 그래서 이 조사의 값어치 대부분이 여기서 나온다.

### 조사 중 알게 된 것 하나 — 사용자가 알고 있던 것과 다르다

`act-nutv4-ac60` 을 "RealSense + GelSight(촉각)" 구성으로 알고 있었으나,
**공개된 설정 파일에 촉각 입력이 없다.** 카메라 2대와 관절 상태뿐이다.
`act-newblue-gs0-ac60` 에는 촉각 관련 설정 항목이 **있지만 꺼져 있고** 입력에도 없다.

→ **공개된 ACT 모델 두 개는 둘 다 촉각을 쓰지 않는다.** 손끝 센서가 없는 우리
구성([`../CLAUDE.md`](../CLAUDE.md) 하드웨어 표)에는 오히려 유리한 사실이다.

## 1. 가장 큰 수확 — 그쪽 코드가 공개돼 있다

`Kaz55/dexwild-training-custom-code` (Hugging Face **데이터셋** 자리,
`dexwild_custom_code.tar.gz`, 191,193 바이트) 에 본인이 쓴 코드가 올라와 있다.
공개 GitHub(`dexwild/dexwild-training`) 에는 이 파일들이 **없다** — 파일 58개를
전수 대조해 확인했다.

들어 있는 것 중 값어치 있는 것:

| 파일 | 무엇 |
|---|---|
| `dit_policy/serve_policy.py` | 정책을 서비스하는 서버 전체 소스 (8000번 포트) |
| `dit_policy/experiments/task/rdm_dg5f_joint_abs.yaml` | **DG-5F 전용 설정** — 무엇을 보고 무엇을 내놓는지 |
| `dit_policy/data4robotics/transforms.py` | 이미지 전처리 |
| `z_helper_scripts/h5_processing/h5_to_lerobot.py` | 로봇 기록 → 학습용 자료 변환 |
| `DEXWILD_INFERENCE.md` | **일본어로 쓴 인수인계 문서** — 무엇이 되고 무엇이 안 되는지 표 |

### 🛑 없는 것 — 실제 로봇을 움직이는 부분

`inference_dg5f.py`(카메라를 잡고 팔·손에 명령을 보내는 프로그램)는 **공개본에 없다.**
그쪽 문서가 로봇 쪽 프로그램을 **"미구현"** 이라고 적어 놓았다.

**즉 "생각하는 쪽"은 소스가 있고, "몸통 쪽"은 설계도만 있다.** 설계도는 꽤 구체적이다 —
어떤 자리에서 팔 6개와 손 20개 상태를 읽어 26칸으로 잇고, 받은 26칸을 팔 명령 자리와
손 명령 자리로 어떻게 나눠 보내는지가 적혀 있다.

그리고 **그쪽도 실물로는 확인하지 못했다** — 가짜 값으로 배관이 도는 것까지만 봤다고
같은 문서에 적혀 있다.

## 2. 세 모델이 무엇을 보고 무엇을 내놓는가

### 보는 것 (입력)

| | act-newblue-gs0-ac60 | act-nutv4-ac60 | dexwild-dit ...v5v6 |
|---|---|---|---|
| 컬러 사진 | **2장** (`realsense1`, `realsense2`), 각 3×480×640 | **2장** | **4장** (카메라 2 + 촉각 카메라 2) |
| 깊이 | 안 씀 | 안 씀 | 안 씀 |
| 점 덩어리 | 안 씀 | 안 씀 | 안 씀 |
| 관절 상태 | **26칸** | **26칸** | **26칸** |
| 촉각 | 설정은 있으나 꺼짐 | 항목 자체가 없음 | 촉각 카메라를 **일반 사진으로** 취급 |
| 사진 크기 | 224×224 로 줄이고 ImageNet 기준 정규화 | 같음 | 같음 |
| 몇 프레임 | 사진 1장 | 사진 1장 | 사진 1장 + **관절 상태는 직전 2개 + 현재 = 3개** |

**셋 다 깊이도 점 덩어리도 쓰지 않는다.** 전부 컬러 사진만 본다.
우리가 D405 의 깊이를 쓰려는 것과는 다른 계통이다.

**26칸의 정체**는 데이터에 이름으로 박혀 있다 — `ur5e_0`…`ur5e_5` + `dg5f_0`…`dg5f_19`.
**앞 6칸이 팔, 뒤 20칸이 손.** 우리 결합 URDF(`urdf/ur16e_dg5f_right_build/`)도 같은
순서(팔 6 + 손 20)다.

### 내놓는 것 (출력)

셋 다 **26칸, 관절 각도의 절대값**이다(설정에 `action_space: "joint_abs"`).
속도도 토크도 아니고, 손목의 위치·방향(end-effector pose)도 아니다.

- ACT 두 모델은 한 번 추론에 **60스텝치를 한꺼번에** 내놓고 줄 세워 하나씩 꺼내 쓴다.
  30 Hz 기준 약 2초 분량.
- `dexwild-dit ...v5v6` 도 청크 60, 20만 스텝 학습본이다.

**미확인**: 이 값이 라디안인지 도(°)인지 공개본 안에서 근거를 못 찾았다. 우리 쪽은
URDF·시뮬레이터가 라디안, 실물 손 SDK(`vision/dg5f/dg5f_sdk_bridge.py`)가 **도(°)** 라서
이 지점은 실물로 확인해야 한다.

**성질 하나** — 여기서 "행동"은 **로봇이 실제로 간 결과가 아니라 사람이 조종 장치로 보낸
목표값**이다(`ur_gello_joint_position`, `dg5f_right_joint_cmd`). 나중에 우리가 데이터를
모을 때도 같은 규칙을 지켜야 한다.

## 3. 그대로 쓸 수 있나 — 없다

| # | 막히는 지점 | 왜 |
|---|---|---|
| **1** | **팔이 다르다 (UR5e vs UR16e)** | **이것 하나로 끝난다.** 관절 수는 6개로 같지만 팔 길이가 다르다. 출력이 **관절 각도 절대값**이라 같은 각도를 넣으면 손끝이 전혀 다른 자리에 간다. 보정으로 메울 수 있는 종류가 아니다 |
| **2** | **카메라 개수·위치가 다르다** | 모델은 사진 **2장을 요구**하는데 우리는 D405 **1대**다. 입력 자리 수부터 안 맞아 실행 자체가 안 된다 |
| **3** | **손목 카메라 장착값이 없다** | 카메라가 손목 어디에 어떤 방향으로 붙었는지가 `config/rtauto_config.py` 에 **아예 없다**(리포 전체 확인 — BACKLOG D-6 이 맞다). 본 것을 로봇 좌표로 옮길 수 없다 |
| **4** | **배운 작업이 다르다** | 저쪽은 케이블 꽂기·너트 조립 같은 정해진 작업. 우리는 "처음 보는 물체 집기" |
| **5** | 손 20관절 내부 순서 | 같은 DG-5F 오른손이라 맞을 가능성이 높지만 **대조하지 못했다** |

**우리 쪽 준비 상태는 좋다** — URDF / 실물 손 SDK / 시뮬레이터 / Unity 표시
**네 곳의 손 관절 순서가 서로 일치하는 것을 확인했다.** 26칸 구조 자체는 맞출 수 있다.

## 4. 그래서 무엇을 가져오나 — 코드 구조만

3장의 1·2번만으로 **학습된 가중치의 값어치는 사실상 0** 이다.
반대로 아래 다섯 가지는 그대로 가져올 값어치가 있다.

1. **26칸 배치 규약** — 앞 6 팔, 뒤 20 손
2. **사진 224×224 + ImageNet 기준 정규화**
3. **관절 상태를 직전 2개 + 현재로 쌓기**
4. **한 번에 60스텝 예측 → 줄 세워 꺼내 쓰기**
5. **"생각하는 쪽"과 "몸통 쪽"을 네트워크로 분리**

### 5번이 우리 문제를 정확히 푼다 — 파이썬 버전이 갈려 있다

| 쪽 | 파이썬 | 근거 |
|---|---|---|
| 파지 학습 (`superdex/`) | **3.12** | `requirements-superdex.txt` |
| 로봇·비전 (`vision/`, `arm/`) | **3.10.11** | `requirements-vision.txt`, 원칙 2 |

**이 둘은 한 프로그램 안에 못 들어간다.** Kaz55 처럼 가운데를 네트워크로 끊으면
3.12 쪽 정책과 3.10 쪽 로봇 제어를 **동시에 돌릴 수 있다**. 지금은 이 문제를
정면으로 다룬 적이 없다.

### 코드 흐름 — 확인한 것과 없는 것

| 단계 | 어디 | 상태 |
|---|---|---|
| 카메라 잡기 | — | ❌ 공개본에 없음 |
| 사진 전처리 | `dit_policy/data4robotics/transforms.py` | ✅ 224×224 축소 + ImageNet 정규화. 학습 땐 흔들기(자르기·흐리기) 추가, 실행 땐 단순 축소+정규화 |
| 관절 상태 합치기 | 보내는 쪽 몫 | ⚠️ 서버가 안 해 준다. **보내는 쪽이 팔 6 + 손 20 순서로 이어붙여야** 한다 |
| 정책 추론 | `dit_policy/serve_policy.py` | ✅ 8000번 포트. 접속하면 **"이런 순서로 보내라"는 안내를 서버가 먼저 돌려준다**(코드에 박은 값이 아니라 체크포인트에 실려 온 설정 그대로) |
| 26칸 받기 | 같은 파일 | ✅ 60스텝 × 26칸 |
| 실제 로봇 명령 | — | ❌ 공개본에 없음 (문서에 "미구현") |

**참고**: LeRobot 본체에 UR 계열도 Tesollo 손도 지원 코드가 **없다**. 로봇 폴더를
전수 확인했다(있는 것: koch, so_follower, lekiwi, reachy2, unitree_g1 등).
**팔·손 연결은 누가 만들어 주지 않는다.**

## 5. 카메라 2대 → D405 1대로 줄이려면

| 고칠 곳 | 무엇 |
|---|---|
| 모델 입력 설정 | 둘째 카메라 항목을 지우고 카메라 수를 1로 |
| `dexwild` 쪽 | 카메라 켬/끔 스위치가 이미 있다 (`camera_mask`) |
| **학습** | ⚠️ **다시 해야 한다.** 카메라 수가 바뀌면 신경망 입구 모양이 바뀐다 |
| 깊이 | **새로 붙여야 한다** — 이 모델들은 컬러만 받는다 |

### 진짜 문제는 코드가 아니다

**손목 카메라 1대만 쓰면 다가가는 동안 물체가 화면 밖으로 나간다.** 가까워질수록 시야가
좁아지고 마지막엔 손가락에 가려진다. 카메라 2대 구성은 이걸 피하려던 것이다.

→ 우리 계획의 **"보고 → 정하고 → 가고 → 다시 보기"**
([`FESTA_PREGRASP_PLAN.md`](FESTA_PREGRASP_PLAN.md) §1)가 이 문제를 이미 피해 간다.
멀리서 보고 목표를 정한 뒤 계산으로 이동하므로 가는 동안 계속 볼 필요가 없다.
**지금 고른 방식이 카메라 1대 구성에 더 잘 맞는다.**

## 6. 손 20관절을 어떻게 표현하나 — 특별한 게 없다

**20개 숫자를 팔 6개 뒤에 그냥 나란히 붙인다.** 손가락별로 묶거나 따로 처리하지 않는다.
각도만 넣고, 나가는 것도 같은 순서 26칸이며 받는 쪽에서 앞 6 / 뒤 20 으로 잘라 보낸다.

우리 쪽 순서 (확인함):

| 어디 | 순서 | 단위 |
|---|---|---|
| URDF (정본) | `rj_dg_1_1` … `rj_dg_5_4` (손가락당 4개) | 라디안 |
| 실물 손 SDK | `thumb_cmc` … `pinky_pip` 20채널, 재배열 없음 | **도(°)** |
| 시뮬레이터 | 팔 0~5, 손 6~25 | 라디안 |
| Unity 표시 | URDF/SDK 와 같은 순서 | 도(°) |

⚠️ **함정**: 시뮬레이터(`superdex/envs/dg5f_grasp_env.py`)는 손 관절을 확인할 때
**이름에 `dg5f` 가 들어있는지만 본다.** 손 20개 **내부 순서가 URDF 와 같은지는 검사하지
않는다.** 외부 정책을 꽂거나 순서를 손댈 때 조용히 어긋날 수 있는 자리다.

## 7. 촉각이 없으니 전류·속도를 넣을 수 있나 — 넣을 수 있다. 선례도 있다

Kaz55 데이터에는 속도와 힘/전류가 **26칸씩 이미 들어 있다.**
다만 **정책 입력에서는 뺐다.** 왜 뺐는지는 적혀 있지 않다.

우리 판단:

- **값어치는 있다.** 손끝 센서가 없는 우리에게 모터 전류는 "닿았다"를 알 수 있는
  거의 유일한 신호다.
- **그런데 지금 계획에는 쓸 자리가 없다.** 현재 목표는 **닿기 전에 멈추는 것**이라
  전류가 변할 일이 없다. **접촉 이후 단계를 할 때 필요해진다.**
- 넣는 방법은 간단하다 — 26칸을 46칸(+손 전류 20)이나 66칸으로 늘린다. 다만 **입구
  모양이 바뀌므로 다시 학습해야 한다.**
- 실무 주의: 전류는 **자세와 온도에 따라 가만히 있어도 값이 변한다.** 무부하 기준값을
  먼저 재서 빼 주지 않으면 잡음만 늘린다.

## 8. D(R,O) Grasp — 양 끝은 우리 것이 있고 가운데가 막힌다

`github.com/zhenyuwei2003/DRO-Grasp` (MIT, ICRA 2025, arXiv:2410.01702).

| 단계 | 판정 | 근거 |
|---|---|---|
| D405 깊이 → 점 덩어리 | 🟡 가능하나 **코드 없음** | 리포에 D405 SDK 를 쓰는 코드가 **하나도 없다**. 설정값(화각 87°/58°, 0.07~0.50 m)만 있고 **실측 전** |
| 물체 분리 | 🟡 없음 | 만들어야 한다 |
| **파지 자세 생성** | 🔴 **막힌다** | 아래 |
| 손목 자세 + 손 목표각 | 🟡 위 때문에 품질 미지수 | — |
| **팔 관절각 계산** | 🟢 **이미 있다** | `arm/prepose_to_joints.py`, 도달 오차 0.0000 mm |
| **로봇 실행** | 🟢 **이미 있다** | `arm/ur_rtde_bridge.py` (가짜 팔에서 확인, 실물 미확인) |

**왜 가운데가 막히나:**

1. 학습된 손이 **3종**(Barrett, Allegro, ShadowHand)뿐. DG-5F 는 없다.
2. 새 손을 넣으려면 **그 손 전용 파지 데이터를 새로 만들고 재학습해야 하는데, 데이터를
   만드는 코드가 저장소에 없다** — 저자가 이슈 답변에서 직접 밝혔다.
3. 저자 본인이 **"구조가 많이 다른 손은 그냥 넣어서 쓰기 어려울 수 있다"** 고 인정했다.
   DG-5F-M(5손가락 20관절)이 정확히 그 경우다.
4. 신경망이 **관절 각도를 직접 내놓지 않는다.** 로봇 표면 점과 물체 표면 점 사이
   **거리표**만 예측하고, 실제 각도는 뒤에 붙는 **별도 최적화(64회 반복)** 로 푼다.
5. **한쪽에서만 본 점 덩어리로 검증된 적이 없다.** 코드의 "일부만 보임" 모드는 카메라
   시점 흉내가 아니라 **평면으로 반 잘라낸 근사**다. 저자들도 실물에서는 카메라 대신
   **휴대폰 3D 스캔**을 썼다.
6. 파이썬 3.8 고정 — 우리 두 환경(3.10.11 / 3.12) 어느 쪽과도 안 맞아 **세 번째 환경**이
   필요하다.

**결론**: 가운데를 D(R,O) 로 메우려면 결국 **재학습**이고, 그건 우리가 D-2/D-4 로 이미
하고 있는 일과 비용이 비슷하다. 남의 것을 쓰는 이점이 사라진다.

### A 가 지금 안 되는 진짜 이유 — 팔을 끌 수단이 없다

실물이 없어서가 아니다. Kaz55 는 `gello` 라는 **팔 조종 장치**로 팔을 끌면서 기록했다.
우리한테는 그게 없다.

> 💡 **손 쪽은 이미 있다.** 웹캠으로 사람 손을 따라 그리퍼를 움직이는
> `vision/dg5f/` 파이프라인이 정확히 그 조종 장치 역할을 한다.
> **팔 조종 수단만 생기면 A 의 전제가 갖춰진다.**

### B 는 이미 우리가 하고 있는 일이다

[`FESTA_PREGRASP_PLAN.md`](FESTA_PREGRASP_PLAN.md) §3 의 구조 — 시뮬레이터에서 자세를
훑어 채점표를 만들고(D-2), 그걸로 예측기를 가르치고(D-4), 실물에선 계산으로 팔을 옮긴다
— 가 바로 B 다. 8장 결론에 따라 **남의 생성기를 가져오는 것보다 우리 것을 계속하는 게
싸다.**

### 권고 — C → B 순서, A 는 나중에

1. **C 를 먼저 뚫는다.** D405 가 도착하면 곧바로: 깊이 → 점 덩어리 → 물체 위치 →
   팔 관절각 계산 → 실제 이동. **이 배관은 B 에 그대로 재사용된다** — "물체 위치"를
   주던 자리를 예측기로 바꾸기만 하면 된다. 버리는 일이 아니다.
2. **그 전에 BACKLOG D-6(손목 카메라 장착값 설정 자리)이 먼저다.** 지금 리포에 그 항목이
   **하나도 없다.** 없으면 카메라가 와도 본 것을 로봇 좌표로 못 옮긴다.
3. **B 는 시뮬레이터 안에서 계속 진행** (D-2 → D-3 → D-4). 장비와 무관하다.
4. **A 는 팔 조종 수단이 생기고 실물이 안정된 뒤에 다시 판단한다.**

## 10. 확인하지 못한 것

정직하게 남긴다. 이어받는 사람이 여기부터 파면 된다.

- **각도 단위(라디안 / 도)** — 공개본 안에 근거가 없다. 실물로 확인해야 한다.

- LeRobot 에서 학습된 정책이 실제로 로봇에 명령을 보내는 루프의 위치 — 못 찾았다.
