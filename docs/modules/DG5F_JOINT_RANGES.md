# 실물 DG-5F-M 관절 각도 — 제조사 설명서 정리

우리 그리퍼(**DG-5F-M-R, 오른손**)의 관절 20개가 **각각 몇 도까지 움직이는지**, 그리고
**어느 쪽이 플러스 방향인지**를 제조사 설명서에서 그대로 옮겨 적은 문서다.

> **출처**: `[테솔로] DG-5F-M_하드웨어_설명서_KR_v2_0_0.pdf`
> — §3.3.1 "모터 순서 및 구동 범위"(19~22쪽), §3.3.2 "모터 방향"(23~24쪽),
> §3.1 "기본 정보"(12쪽), §3.1.2 "Zero Position"(15~16쪽).
> (2026-09-16 정리. PDF는 저장소에 없다 — 바탕화면 `dg5f/` 폴더에 있는 원본을 본다.)

> ⚠️ **이 문서는 설명서의 사본이고, 코드가 쓰는 값의 정본이 아니다.** 프로그램이 실제로
> 읽는 값은 아래 §5에 적힌 코드 안의 표들이다(원칙 1 — 같은 숫자를 두 곳에 타이핑하지
> 않는다). 여기서는 "설명서가 뭐라고 하는지"와 "코드가 그것과 맞는지"만 확인한다.

| 설명서 | 우리가 부르는 이름 | 비고 |
|---|---|---|
| Finger 1 | 엄지 | 손바닥 옆에서 마주 보는 손가락 |
| Finger 2 | 검지 | |
| Finger 3 | 중지 | |
| Finger 4 | 약지 | |
| Finger 5 | 새끼 | |

모터는 1번부터 20번까지 있고, **엄지부터 새끼까지 손가락당 4개씩 순서대로** 붙어 있다.

이 대응은 2026-08-31에 실물로 확인됐다(`vision/dg5f/dg5f_sdk_bridge.py` 주석 참고).

## 4. 0도는 어디이고, 플러스는 어느 쪽인가

- **0도(Zero Position, 설명서 15쪽)**: 네 손가락이 **쭉 펴져 손바닥과 한 평면**에 있고,
  엄지는 **옆으로 뻗어 손바닥 평면에 누운** 자세. 모든 관절값이 0일 때의 모습이다.
- **플러스 방향(설명서 23쪽)**: 도면의 **빨간 화살표 방향이 +**. 손가락 굽힘은
  **오므리는 쪽이 +**이고, 이는 우리 코드 규약(굽힘=양수)과 같다 — 그래서
  `dg5f_sdk_bridge.py`의 부호 변환표(`JOINT_SIGN`)가 전부 +1이다.
- ⚠️ **엄지 마주보기(1_2, Motor 2)만 예외**: 설명서 표는 "0 ~ 155"로 적혀 있지만 그건
  **부호 없는 이동량** 표기다. 실물 엔코더와 명령은 URDF와 같은 **음수** 규약을 쓰며,
  실측에서 +3.7°에 기구 한계가 확인됐다. 그래서 코드는 이 관절만 −155° ~ 0°로 둔다
  (근거는 `dg5f_sdk_bridge.py`의 해당 줄 주석).

## 5. 이 숫자들이 코드 어디에 들어 있나

| 어디 | 무엇 | 이 문서와의 관계 |
|---|---|---|
| `vision/dg5f/dg5f_sdk_bridge.py` → `JOINT_CLAMP_RIGHT` | 실물로 나가는 명령을 자르는 한계값 | 기본은 **§2 표와 같다.** 단 **설명서보다 좁다는 근거(URDF·실측)가 있으면 좁은 쪽을 쓴다** — 지금 그런 채널은 `thumb_opp`(실측 하드 스톱)와 `middle_abd`(URDF) 둘이다 |
| `urdf/dg5f/dg5f_right.urdf` 등 `<limit>` | Unity·시뮬레이터가 쓰는 한계값 | 설명서와 같아야 한다(라디안 단위) |
| `vision/dg5f/dg5f_angles.py` → `URDF_LIMITS_DEG` | 비율 매핑이 쓰는 **왼손 URDF** 한계값 | §3 왼손 표와 같아야 한다 |
| `vision/dg5f/dg5f_angles.py` → `DG5F_CHANNELS` | **실제로 쓰는(더 좁은) 범위** | §6 참고 — 일부러 좁혀 둔 값이다 |
| `vision/dg5f/joint_ranges.py` → `SPEC` | 사람 손 범위 ↔ 로봇 범위 대조표 | 확인용(`python joint_ranges.py`) |

### 20개 전수 대조 결과 (2026-09-16)

URDF 파일에서 관절 20개의 한계를 직접 읽어 코드의 두 표와 맞춰 봤다.

| 대조 | 결과 |
|---|---|
| `URDF_LIMITS_DEG` ↔ 왼손 URDF | **20개 전부 일치.** 코드가 URDF 를 잘못 옮긴 곳은 없다 |
| 왼손 URDF ↔ 오른손 URDF | 6개가 다르고(`thumb_cmc` `thumb_opp` `index_abd` `ring_abd` `pinky_cmc` `pinky_lat`) **전부 §4 의 좌우 뒤집기 규약대로**다 |
| `JOINT_CLAMP_RIGHT` ↔ 오른손 URDF | **20개 전부 일치**(아래 `middle_abd` 를 고친 뒤) |

재현: `python -c` 로 URDF 의 `<limit lower= upper=>` 를 읽어 도(°)로 바꿔 비교하면 된다.
URDF 값은 라디안이다 — 예: `0.4363323129985824 rad = 25.0°`.

### 제조사 자료 두 개가 서로 다른 곳

| 채널 | 설명서 | 제조사 URDF | 우리가 쓰는 값 | 왜 |
|---|---|---|---|---|
| `middle_abd` | −30° ~ +30° | **±25°** (좌우 양손 모두) | **±25°** (2026-09-16 좁힘) | 실측할 방법이 없는 동안에는 **좁은 쪽**을 쓴다. 클램프는 안전 한계라 좁아도 위험하지 않지만, 넓으면 하드 스톱에 밀어붙일 수 있다. 이걸 좁히면서 클램프 20개가 URDF 와 전부 맞게 됐다 |
| `thumb_opp` | 0° ~ 155° | −155° ~ 0° | −155° ~ 0° | §4 의 부호 규약 때문이다(**의도된 차이**). 게다가 실측에서 **+3.7°에 하드 스톱**이 확인돼 상한을 0 으로 잡았다 |

> 🛑 **`middle_abd` 를 ±30 으로 되돌리려면 실물로 재서 확인한 뒤**, 여기와
> `urdf/dg5f/*.urdf` 네 파일을 **함께** 넓혀야 한다. 한쪽만 넓히면 다시 어긋난다.
> 지금은 이 관절이 아예 안 쓰이므로(§6 — 항상 0) 동작에는 차이가 없다.

## 6. ⚠️ 실제로 쓰는 범위는 이보다 훨씬 좁다

`DG5F_CHANNELS`(`dg5f_angles.py`)는 **기구가 낼 수 있는 범위 안에서 다시 좁힌 값**을 쓴다.
사람 손 동작을 그대로 옮기면 로봇이 과장되게 움직이거나, 계산이 지저분한 채널이 로봇을
엉뚱하게 흔들기 때문이다. 벌림 관절만 비교하면:

| 채널 | 기구 한계(오른손) | 지금 쓰는 범위 | 사람 손 실측 폭 |
|---|---|---|---|
| `index_abd` | −31° ~ +20° | −25° ~ +20° | 46° |
| `middle_abd` | 설명서 −30°~+30° / **URDF ±25°**(§5) | **항상 0**(gated) | 3.9°(손 편 상태) |
| `ring_abd` | −15° ~ +32° | −12° ~ +28° | 42° |
| **`pinky_lat`** | **−15° ~ +90°** | **−15° ~ +50°** (2026-09-16 확대) | **102°**(옛 계산식) / 43°(새 계산식) |

**새끼(`pinky_lat`)는 2026-09-16에 고쳤다.** 그 전에는 24° 폭(±12°)만 통과시켜, 보정 기록의
**78.5%가 한계값에 눌려** "새끼를 벌려도 로봇이 따라오지 않는" 증상이 있었다.

좁혀 뒀던 이유는 좌우값 계산에 **굽힘이 섞여 들어와서**였고(상관 −0.94), 그 원인을 계산식
쪽에서 고친 뒤 범위를 −15°~+50°로 넓혔다. 결과: 로봇 새끼가 따라가는 폭 12.4° → **43.4°**,
한계에 눌린 비율 54.7% → 0.6%. 판정 근거와 재현 방법은
[`VISION_TELEOP.md`](VISION_TELEOP.md) §6-2-2와 `vision/dg5f/analyze_abduction.py`에 있다.
