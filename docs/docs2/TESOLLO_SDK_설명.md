# 회사가 준 Tesollo SDK를 왜 안 썼나? — 쉬운 설명

조사일 2026-07-29. 자세한 근거와 코드 위치는 `docs/TESOLLO_SDK_기술부채_조사.md`.

---

## 1. 한 줄 답

**안 쓴 게 아니다. 쓰고 있다.** 다만 SDK가 해 주지 않는 부분이 있어서, 그 빈자리를
MediaPipe가 채우고 있을 뿐이다.

---

## 2. SDK는 "손"이고 MediaPipe는 "눈"이다

로봇손을 사람 손으로 조종하려면 두 가지가 필요하다.

1. **사람 손이 지금 어떤 모양인지 알아내기** ← 이게 있어야 보낼 값이 생긴다
2. **그 모양대로 로봇손을 움직이기**

**Tesollo SDK는 2번만 해 준다.** SDK 설명서에 있는 기능을 전부 확인해 봤는데,
"손가락 20개를 이 각도로 움직여라"라는 명령을 받아 실행하는 기능은 있지만,
**그 각도를 무엇으로 정할지 알아내는 기능은 하나도 없다.**

비유하자면 SDK는 **자동차의 핸들과 페달**이다. 아주 잘 만들어져 있지만, 어디로
갈지는 알려주지 않는다. 운전자가 필요하다. 이 프로젝트에서 **MediaPipe가 그
운전자** 역할이다. 웹캠으로 사람 손을 보고 손가락 20개의 각도를 계산해 낸다.

```
웹캠으로 내 손을 봄
   ↓  [MediaPipe] ← SDK에 없는 부분
"엄지 30도, 검지 45도, ..." 숫자 20개
   ↓
   ├→ Unity 화면 속 로봇손 (연습·학습용)
   └→ [Tesollo SDK] → 실제 로봇손          ← SDK를 쓰는 부분
```

---

## 3. 제조사도 똑같이 한다

"그럼 원래 SDK만으로 텔레오퍼레이션이 되는 것 아니냐"는 의문이 남는데, **제조사인
Tesollo 자신의 시연 사례를 봐도 SDK 단독이 아니다.** 공식 사례는 **MANUS나
SenseGlove라는 데이터 장갑**을 손에 끼고, 그 장갑이 읽은 값을 SDK로 흘려보내는
방식이다.

즉 **사람 손을 읽는 장치는 어차피 따로 필요하다.** 우리에게는 그 데이터 장갑
(수백만 원대 장비)이 없었고, 대신 **웹캠 + MediaPipe**로 같은 자리를 채웠다.
공짜 장비로 유료 장갑의 역할을 대신한 셈이다.

---

## 4. Unity는 또 왜 필요했나

SDK는 **실제 로봇손이 눈앞에 연결돼 있어야만** 작동한다. 그런데 이 프로젝트의
본체는 강화학습이었다.

- 로봇이 블록 잡는 법을 배우려면 **수백만 번 연습**해야 한다. 실물로는 불가능하다.
- 학습 중에는 로봇이 팔을 테이블에 부딪치는 등 **실물이면 망가질 행동**을 수없이 한다.
- 우리가 다룬 건 손만이 아니라 **UR5e 팔 + 손 전체**다. SDK는 손만 담당한다.

SDK에는 시뮬레이션 기능이 없다. 그래서 Unity가 필요했고, 이건 SDK로 대체할 수 있는
성질의 것이 아니다.

---

## 5. 그럼 진짜 문제는 없나 — 있다, 4가지

"SDK를 안 썼다"는 문제는 아니지만, **"SDK를 제대로 안 썼다"는 문제는 있다.**

### ① 회사가 준 공식 파이썬 도구를 안 쓰고 직접 만들었다 — 가장 시급

회사가 준 자료에는 **파이썬용 공식 도구(`dg_python`)**가 들어 있었다. 예제 4개와
테스트까지 갖춰진 완성품이다. 그런데 우리는 이걸 쓰지 않고, 설계 문서를 보며
연결 코드를 **직접 손으로 다시 만들었다.**

무엇이 문제인가:

- **나중에 SDK가 업데이트되면 우리 코드가 조용히 깨진다.** 에러 메시지가 뜨는 게
  아니라 **엉뚱한 값이 로봇으로 나가는 형태**로 나타나서 알아채기도 어렵다.
- **우리가 만든 건 기능 9개뿐**이다. 공식 도구는 100개가 넘는 기능을 쓸 수 있게
  해 준다. 아래 ③의 센서 기능도 전부 여기 들어 있다.

**참고**: 우리가 만든 코드는 Windows 파일(`DGSDK.dll`)을 쓰도록 돼 있는데,
**팀원 모두 Windows이므로 이건 문제가 아니다.** 공식 도구로 바꾸면 리눅스 파일도
같이 들어 있어 학습용 리눅스 PC에서도 돌아간다는 덤이 있을 뿐이다.

**고치는 법**: 브리지 파일에서 클래스 하나만 공식 도구로 바꿔 끼우면 된다.
나머지 로직은 그대로 둬도 된다.

### ② 실물 로봇에 아직 한 번도 안 돌려봤다 — 안전 문제

우리 코드에는 "우리 1번 손가락 = 실물 1번 손가락"이라는 대응표가 있는데,
**이 표가 맞는지 확인한 적이 없다.** 지금은 "아마 순서대로겠지"라고 가정만
해 둔 상태이고, 코드에도 **"모르면 움직이지 말 것"**이라는 경고가 적혀 있다.

순서나 방향이 틀린 채로 명령을 보내면 **손가락이 꺾이는 방향으로 움직일 수 있다.**
실물을 처음 돌리기 전에 반드시 한 관절씩 조금씩 확인해야 한다.

### ③ 로봇이 보내주는 정보를 하나도 안 받고 있다

지금 우리 시스템은 **명령을 보내기만 하고 아무것도 듣지 않는다.** 눈을 감고
운전하는 것과 같다. 안 쓰고 있는 것들:

| 안 쓰는 기능 | 쓰면 좋은 곳 |
|---|---|
| 손끝 촉각·힘 센서 | "진짜 잡았는지" 실물에서 확인 |
| 관절 실제 위치·전류 | 명령대로 움직였는지 대조 |
| 내장 파지 기능 | 물체를 알아서 쥐는 기능이 이미 있다 |
| 수동 교시 모드 | 사람이 직접 손을 움직여 동작 녹화 |

### ④ 기록을 안 남겼다

SDK 연결 코드를 만든 사실이 작업 기록(`WORKLOG.md`)에 없다. 코드 주석에만 있다.
그래서 **"왜 SDK를 안 썼냐"는 질문이 계속 반복된다.** 이 문서가 그걸 막기 위한
것이다.

## 6. 예상 질문

**Q. SDK에 물체를 알아서 잡아 주는 기능이 있다던데, 그럼 강화학습은 왜 했나?**

내장 파지 기능은 **손 하나만으로 정해진 방식대로 쥐는 것**이다. 우리 과제는
팔이 물체까지 다가가는 경로부터 잡고 들어 올리기까지 전체였고, 그건 손만으로는
안 된다. 다만 **이 둘을 실제로 비교 측정해 본 적은 없다는 점은 인정해야 한다.**

**Q. 그럼 SDK 대신 MediaPipe를 쓴 게 아니라는 건가?**

그렇다. **MediaPipe는 눈, SDK는 손**이고 둘은 일렬로 연결돼 있다. 실제로 코드도
사람 손에서 계산한 값을 Unity(연습용)와 실물 SDK(진짜 로봇)에 **동시에** 보내도록
만들어져 있다.

**Q. 지금 당장 실물을 돌릴 수 있나?**

아니다. 위 ②번(관절 대응 확인)을 먼저 해야 한다. 지금 상태로 돌리면 하드웨어가
손상될 수 있다.
