# 우리가 만든 신경망을 기업이 쓸 수 있나? — 쉬운 설명

작성일 2026-07-29. 기술적 근거와 코드 위치는 `docs/TESOLLO_SDK_기술부채_조사.md` 4.5절,
Tesollo SDK 자체에 대한 설명은 `docs/TESOLLO_SDK_설명.md` 참조.

---

## 한 줄 결론

**사용할 수 있습니다.**  
다만 `DG5FGraspLift.onnx` 파일만 전달한다고 바로 작동하는 것은 아닙니다. 기업 시스템이 신경망에 필요한 **57개의 입력값을 학습 당시와 똑같은 규격으로 만들어 줄 수 있어야 합니다.**

현재 가장 큰 연결 과제는 **카메라 비전으로부터 물체의 위치·속도·기울기를 계산해 25개의 입력값을 만드는 것**입니다.

---

## 1. ONNX 파일은 어떤 것인가?

학습 결과물은 다음 파일 하나입니다.

```text
DG5FGraspLift.onnx
```

ONNX는 특정 프로그램에만 종속된 파일이 아니라, 여러 환경에서 사용할 수 있는 **표준 신경망 형식**입니다.

비유하면 ONNX는 특정 회사의 전용 충전기가 아니라, 여러 장치에서 사용할 수 있도록 규격을 맞춘 **표준 부품**과 비슷합니다. 따라서 기업이 Unity나 ML-Agents를 사용하지 않아도 됩니다.

| 항목 | 확인 결과 |
|---|---|
| Unity 필요 여부 | 필요 없음 |
| ML-Agents 필요 여부 | 필요 없음 |
| 실행 방법 | `onnxruntime` 등으로 직접 실행 가능 |
| 운영체제 | Windows와 Linux 모두 가능 |
| 실제 실행 확인 | `onnxruntime`으로 확인 완료 |
| 1회 판단 시간 | 0.049밀리초 |
| 정해진 판단 주기 | 100밀리초 |
| 판단 시간의 비율 | 판단 주기의 약 0.05% |

신경망은 100밀리초마다 한 번 판단하면 되는데, 실제 판단에는 0.049밀리초만 걸렸습니다. 따라서 **신경망 자체의 실행 속도는 문제가 되지 않습니다.**

---

## 2. 파일만 전달하면 바로 쓸 수 있을까?

그렇지는 않습니다.

ONNX 파일 자체는 다음과 같은 함수일 뿐입니다.

```text
숫자 57개 입력 → 숫자 7개 출력
```

신경망은 입력된 숫자의 의미를 스스로 확인하지 않습니다. 57개의 숫자가 학습 당시와 다른 순서나 단위로 들어와도 오류를 내지 않고 결과를 계산합니다. 문제는 그 결과가 엉뚱할 수 있다는 것입니다.

예를 들어 요리법에 다음과 같이 적혀 있다고 생각해 보겠습니다.

```text
첫 번째 칸: 밀가루 100g
두 번째 칸: 물 50mL
```

그런데 밀가루와 물의 순서를 바꾸거나, 그램 대신 킬로그램 단위로 값을 넣어도 계산기는 오류를 내지 않습니다. 단지 완전히 잘못된 반죽이 만들어집니다.

강화학습 신경망도 마찬가지입니다.

- 57개 값의 **순서**
- 각 값의 **단위**
- 값의 **방향과 기준 좌표**
- 값의 **계산 방법**
- 필요한 경우 값의 **정규화 방법**

이 모두가 학습 때와 같아야 합니다.

따라서 기업에 실제로 넘겨야 할 핵심은 단순히 ONNX 파일 하나가 아닙니다.

> **진짜 납품 대상은 `DG5FGraspLift.onnx`와 함께 제공되는 “입력 숫자 57개를 만드는 규격”입니다.**

ONNX가 자동차의 엔진이라면, 57개 입력 규격은 연료·전기·센서를 올바르게 연결하는 배선도입니다. 좋은 엔진도 배선이 잘못되면 제대로 움직일 수 없습니다.

## 3. 입력 숫자 57개는 어디에서 오는가?

입력 57칸은 출처에 따라 다음 네 종류로 나뉩니다.

| 입력값의 출처 | 칸 수 | 현재 조달 가능 여부 | 설명 |
|---|---:|---|---|
| 로봇팔 컨트롤러와 우리가 보낸 값 | 19칸 | 가능 | 기업 시스템에 이미 있는 값 |
| Tesollo SDK 손끝 센서 | 7칸 | 가능 | Tesollo SDK를 통해 받을 수 있는 값 |
| 앞의 값들로 계산하는 파생값 | 6칸 | 가능 | 이미 얻은 값을 이용해 계산 |
| 카메라 비전 | 25칸 | 현재 없음 | 블록의 위치·속도·기울기 등에 의존 |
| **합계** | **57칸** |  |  |

### 이미 마련할 수 있는 입력: 32칸

다음 값들은 기업 시스템이나 Tesollo SDK에서 얻을 수 있거나, 얻은 값으로 계산할 수 있습니다.

```text
19칸 + 7칸 + 6칸 = 32칸
```

즉, 57칸 중 32칸은 현재 연결 방법이 있습니다.

### 아직 필요한 입력: 비전 관련 25칸

남은 25칸은 카메라가 관찰한 블록의 정보에 의존합니다.

대표적으로 다음과 같은 정보가 필요합니다.

- 블록의 위치
- 블록이 움직이는 속도
- 블록이 기울어진 정도

따라서 현재의 핵심 과제는 ONNX 실행이 아니라, **실제 카메라 영상에서 필요한 정보를 계산하여 정확한 순서와 단위로 25칸에 넣는 비전 연결부**를 만드는 것입니다.

## 4. 신경망이 내보내는 7개 출력은 어떻게 사용되는가?

신경망의 출력은 총 7개입니다.

| 출력 | 개수 | 사용처 |
|---|---:|---|
| 로봇팔 관절 명령 | 6개 | UR5e 팔 제어기 |
| 로봇손 닫힘 명령 | 1개 | 20개 손가락 관절 각도로 변환 후 Tesollo SDK |
| **합계** | **7개** |  |

### 로봇손 출력은 바로 연결할 수 있다

신경망이 내보내는 손 명령은 1개입니다. 이 값은 손의 닫힘 정도를 뜻하며, 20개의 관절 각도로 변환됩니다.

변환된 값은 다음 Tesollo SDK 함수에 그대로 전달할 수 있습니다.

```text
move_servo_joint(20개 관절 각도)
```

즉, 손 부분은 처음부터 **Tesollo SDK 규격에 맞도록 설계**했습니다.

자격증에 비유하면, 손 제어 부분은 이미 Tesollo SDK라는 현장에서 인정되는 자격증을 가지고 있는 셈입니다. 별도의 통역 규칙을 새로 만드는 것이 아니라, 기존 SDK 연결 방식에 맞춰 사용할 수 있습니다.

### 로봇팔 출력에는 별도의 제어기가 필요하다

나머지 6개 출력은 UR5e 로봇팔의 관절을 움직이기 위한 값입니다.

Tesollo SDK는 로봇손을 위한 도구이므로 UR5e 팔 제어는 담당하지 않습니다. 따라서 팔 출력 6개를 실제 움직임으로 바꾸려면 **UR5e 팔 제어기가 별도로 필요합니다.**

정리하면 다음과 같습니다.

```text
신경망 출력 7개
├─ 팔 출력 6개 → UR5e 팔 제어기
└─ 손 출력 1개 → 20개 관절 각도로 변환
                  → Tesollo SDK move_servo_joint()
```

## 5. 기업이 원한 시스템과 어떻게 연결되는가?

기업이 원래 원한 것은 **카메라로 상황을 보고 로봇을 실시간으로 제어하는 시스템**입니다.

우리가 만든 신경망은 전체 시스템 가운데 **비전 뒤에 붙는 두뇌**에 해당합니다.

| 사람에 비유한 구성 | 실제 시스템 |
|---|---|
| 눈 | 카메라 |
| 본 것을 이해하는 과정 | 비전 처리 |
| 어떻게 움직일지 결정하는 두뇌 | `DG5FGraspLift.onnx` |
| 팔과 손에 명령을 전달하는 신경 | UR5e 제어기와 Tesollo SDK |
| 실제 신체 | UR5e 로봇팔과 Tesollo 로봇손 |

현재 두뇌인 ONNX는 준비되어 있습니다. 손으로 명령을 보내는 연결 방식도 준비되어 있습니다. 팔은 별도의 UR5e 제어기를 연결해야 합니다.

가장 중요한 미완성 부분은 **카메라 영상으로부터 신경망이 요구하는 비전 입력 25개를 만드는 과정**입니다.

> 따라서 비전 입력만 정확한 규격으로 연결되면 기업 시스템에서 사용할 수 있습니다.

## 6. 실제 적용을 위해 필요한 연결 구조

전체 흐름은 다음과 같습니다.

```text
카메라 영상
    ↓
비전 처리
- 블록 위치
- 블록 속도
- 블록 기울기
    ↓
비전 관련 입력 25개 생성
    +
기존 로봇·센서·파생 입력 32개 생성
    ↓
학습 때와 같은 순서·단위로 57개 조립
    ↓
DG5FGraspLift.onnx
    ↓
출력 7개
    ├─ 팔 6개 → UR5e 팔 제어기
    └─ 손 1개 → 20개 관절 각도로 변환
                 → Tesollo SDK
```

기업 적용에 필요한 작업을 요약하면 다음과 같습니다.

| 작업 | 상태 |
|---|---|
| ONNX 파일 실행 | 확인 완료 |
| Windows/Linux 실행 | 가능 |
| 실행 속도 | 문제없음 |
| 로봇팔 관련 입력 연결 | 기업 시스템의 기존 값 사용 가능 |
| Tesollo 손끝 센서 입력 연결 | SDK로 가능 |
| 파생 입력 계산 | 앞의 값으로 계산 가능 |
| 손 출력 연결 | Tesollo SDK에 맞게 설계 완료 |
| 팔 출력 연결 | UR5e 팔 제어기 필요 |
| 카메라 비전 입력 25개 생성 | 추가 구현 필요 |
| 실제 환경의 카메라 노이즈 대응 검증 | 아직 필요 |

## 7. 반드시 정직하게 남겨야 할 한계

시뮬레이터와 실제 카메라는 물체를 보는 방식이 다릅니다.

시뮬레이터는 물체의 정확한 위치를 내부적으로 알고 있으므로 **오차 0인 위치 정보**를 제공할 수 있습니다. 그러나 실제 카메라에는 다음과 같은 문제가 생깁니다.

- 측정값이 조금씩 흔들리는 노이즈
- 촬영과 처리에 걸리는 시간으로 인한 지연
- 조명 변화
- 물체가 가려지는 현상
- 위치나 기울기 추정 오차

계량스푼에 비유하면, 시뮬레이터는 매번 정확히 같은 양을 담아 주는 완벽한 계량기입니다. 실제 카메라는 사람이 눈금을 보며 재는 계량스푼과 같아서 약간의 오차와 시간 차이가 생깁니다.

학습 과정에서는 이러한 차이를 견디도록 입력값에 다양한 오차와 변화를 일부러 섞는 **도메인 랜덤화**를 하지 않았습니다.

따라서 현재 확인된 사실은 다음과 같습니다.

> ONNX 파일이 기업 시스템에서 실행되고 충분히 빠르게 판단할 수 있다는 것은 확인했습니다.  
> 그러나 실제 카메라의 노이즈와 지연이 있어도 정책이 안정적으로 동작하는지는 아직 검증되지 않았습니다.

이는 “사용할 수 없다”는 뜻이 아니라, 실제 적용 전에 다음 검증이 필요하다는 뜻입니다.

1. 실제 카메라로 비전 입력 25개를 생성합니다.
2. 학습 당시의 입력 순서와 단위를 정확히 맞춥니다.
3. 카메라 노이즈와 지연이 있는 상태에서 로봇 동작을 시험합니다.
4. 불안정하다면 노이즈와 지연을 반영해 추가 학습하거나 정책을 보완합니다.

## 8. 예상 질문 Q&A

### Q1. Unity를 기업 시스템에도 설치해야 하나요?

아닙니다. ONNX는 프로그램 종류를 가리지 않는 표준 형식이므로 Unity나 ML-Agents 없이 실행할 수 있습니다. 실제로 `onnxruntime`으로 실행을 확인했습니다.

### Q2. Windows에서만 사용할 수 있나요?

아닙니다. Windows와 Linux 모두에서 사용할 수 있습니다.

### Q3. 신경망이 너무 느려서 실시간 제어가 어려운 것은 아닌가요?

신경망의 실행 속도는 문제가 되지 않습니다. 1회 판단에 0.049밀리초가 걸렸으며, 정해진 판단 주기 100밀리초의 약 0.05%에 불과합니다.

다만 전체 시스템의 실시간 성능은 카메라 촬영, 비전 처리, 통신, 로봇 제어 시간까지 함께 확인해야 합니다.

### Q4. ONNX 파일 하나만 전달받으면 바로 사용할 수 있나요?

아닙니다. ONNX는 숫자 57개를 받아 숫자 7개를 내보내는 함수일 뿐입니다. 입력값의 순서와 단위가 학습 때와 정확히 같아야 합니다.

따라서 ONNX 파일과 함께 **57개 입력값의 순서·단위·계산 방법을 정의한 규격서**가 필요합니다.

### Q5. 입력값의 순서가 조금 달라도 오류가 발생하나요?

대부분 프로그램 오류는 발생하지 않습니다. 더 위험한 점은 오류 없이 잘못된 결과가 나온다는 것입니다.

예를 들어 신경망이 첫 번째 칸을 로봇 관절 각도로 알고 있는데 실제 시스템이 그 칸에 블록 위치를 넣으면, 신경망은 이를 구분하지 못합니다.

### Q6. 현재 바로 만들 수 있는 입력은 몇 개인가요?

57개 중 32개입니다.

- 기업 시스템에 이미 있는 값: 19개
- Tesollo SDK 손끝 센서값: 7개
- 앞의 값으로 계산하는 파생값: 6개

나머지 25개는 카메라 비전 정보에 의존합니다.

### Q7. Tesollo 로봇손은 바로 연결할 수 있나요?

손 쪽 인터페이스는 처음부터 Tesollo SDK 규격에 맞춰 설계했습니다. 신경망의 손 닫힘 출력 1개를 20개의 관절 각도로 변환한 뒤 `move_servo_joint(20개 각도)`에 전달할 수 있습니다.

### Q8. UR5e 로봇팔도 Tesollo SDK로 제어하나요?

아닙니다. Tesollo SDK의 범위는 로봇손입니다. 신경망의 팔 출력 6개를 사용하려면 별도의 UR5e 팔 제어기가 필요합니다.

### Q9. 카메라 입력만 연결하면 실제 현장에서 바로 안정적으로 동작하나요?

그렇게 단정할 수는 없습니다. 시뮬레이터는 물체 위치를 오차 없이 제공하지만 실제 카메라에는 노이즈와 지연이 있습니다.

학습할 때 도메인 랜덤화를 하지 않았기 때문에, 정책이 이러한 차이를 견딜 수 있는지는 아직 검증되지 않았습니다. 실제 장비를 이용한 시험이 반드시 필요합니다.

### Q10. 그렇다면 현재 결과물의 정확한 의미는 무엇인가요?

기업이 원한 전체 시스템 중 **비전 결과를 받아 로봇팔과 로봇손의 움직임을 결정하는 두뇌**를 만든 것입니다.

두뇌는 실행 가능하고 속도도 충분합니다. 다만 두뇌가 이해할 수 있는 정확한 형태로 카메라 정보를 전달하는 비전 연결부와, 실제 환경의 오차를 견디는지 확인하는 검증 과정이 남아 있습니다.

## 최종 결론

`DG5FGraspLift.onnx`는 Unity나 ML-Agents 없이 Windows와 Linux에서 실행할 수 있으며, 실제 측정된 판단 시간도 0.049밀리초로 충분히 빠릅니다.

그러나 이 파일은 완성된 로봇 제어 프로그램 전체가 아니라, **57개의 숫자를 받아 7개의 제어값을 결정하는 두뇌**입니다. 따라서 기업 시스템에서 사용하려면 57개 입력을 학습 당시와 동일한 순서·단위·계산 방식으로 만들어야 합니다.

현재 57개 중 32개는 기업 시스템과 Tesollo SDK를 통해 마련할 수 있습니다. 남은 25개는 블록의 위치·속도·기울기와 같은 카메라 비전 정보에 의존합니다. 출력에서는 손 제어가 Tesollo SDK 규격에 맞게 준비되어 있고, 팔 제어에는 별도의 UR5e 제어기가 필요합니다.

> **기업이 원한 것은 비전으로 로봇을 실시간 제어하는 시스템이고, 우리가 만든 ONNX는 그 비전 뒤에서 동작하는 두뇌입니다. 비전 입력 25개를 정확한 규격으로 연결하면 기업 시스템에서 사용할 수 있습니다.**

다만 실제 카메라에는 시뮬레이터와 달리 노이즈와 지연이 있으며, 학습 과정에서 도메인 랜덤화를 하지 않았습니다. 따라서 실제 환경에서도 정책이 안정적으로 동작하는지는 아직 검증되지 않았고, 현장 적용 전에 반드시 시험해야 합니다.
