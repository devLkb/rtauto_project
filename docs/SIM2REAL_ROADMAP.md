# Sim2Real 로드맵 — 자율주행 + 웨이퍼 케이스 Pick & Place

작성 2026-08-25 (v2 — 시뮬레이터/미들웨어 아키텍처 확정 반영).
1인 풀타임·로컬 단독 머신(RTX 2080, Windows) 체제.

정책 계약 상세는 [`DG5F_GRASP_LIFT.md`](DG5F_GRASP_LIFT.md), SDK 실측 근거는
[`TESOLLO_SDK_기술부채_조사.md`](TESOLLO_SDK_기술부채_조사.md)를 우선한다.

## 1. 확정된 시스템 아키텍처

| 레이어 | 담당 | 비고 |
|---|---|---|
| 물리·학습 | **MuJoCo** | 접촉 리치 매니퓰레이션. Unity PhysX 대체 |
| 시각화 | **Unity + MuJoCo Unity 플러그인** | 물리 소유권 없음. MJCF를 읽어 렌더링만 |
| 자율주행 | **ROS2 + Nav2 + slam_toolbox** | [Robotics-Nav2-SLAM-Example](https://github.com/Unity-Technologies/Robotics-Nav2-SLAM-Example) 기반 |
| 실물 하드웨어 | UR5e (RTDE) + Tesollo DG5F-M (dgsdk) + 이동 베이스(스펙 미정) | |

**동작은 순차**: 이동 → 정지 → 로봇팔 → 그리퍼.

### 순차 동작이 아키텍처를 단순하게 만든다

두 가지 중요한 결과가 따라온다:

1. **시뮬레이터를 하나로 통합할 필요가 없다.** 주행 시뮬레이션(Unity + Nav2 예제,
   평지 바퀴 주행 — PhysX로 충분)과 매니퓰레이션 시뮬레이션(MuJoCo, 접촉 정밀도 필요)은
   **동시에 돌 일이 없다.** 각 단계에 맞는 시뮬레이터를 따로 쓰면 된다.
2. **정책 관찰 설계가 그대로 유효하다.** 매니퓰레이션 중 베이스는 정지 상태이므로
   기존 obs57이 가정하는 "고정된 로봇 베이스 프레임"이 실물에서도 성립한다.
   모바일 매니퓰레이션(주행 중 파지)은 범위 밖.

## 2. 관찰·액션의 실물 조달 (SDK 조사 반영)

기존 정책은 obs 57 / act 7, 결정주기 0.1 s (10 Hz). 배포 ONNX 시그니처는
`obs_0 [batch,57]` → `deterministic_continuous_actions [batch,7]` 로 확인돼 있어
`onnxruntime`으로 Unity 없이 Python 추론이 가능하다.

### 액션 7 — 경로가 이미 열려 있다

- `[0..5]` 팔: 관절 각도 델타 누적 → `ArmSafeMinDeg/MaxDeg`로 clamp된 절대 목표각.
  **관절공간 위치 제어라 IK 불필요**, UR5e RTDE로 직접 명령.
- `[6]` 그립: 스칼라 closure → `Lerp(openHand, LeftFistDeg, closure)`로 20관절.
  결정적 고정 매핑이고, **기존 브리지가 텔레옵으로 이미 보내는 형식과 동일**하다.
  손가락 20개를 개별 출력하지 않고 스칼라 1개로 묶은 설계가 실물 이식에서 유리하다
  (정책이 물리적으로 불가능한 손 모양을 만들 여지가 구조적으로 없다).

### 관찰 57 — 병목은 **비전 하나**로 좁혀졌다

| 관찰 | 개수 | 실물 조달처 | 가능? |
|---|---:|---|:--:|
| 팔 관절 각도·속도 | 12 | UR5e RTDE | ✅ |
| 팔 명령각 | 6 | 우리가 보낸 값 | ✅ |
| 손 닫힘 | 1 | 우리가 보낸 값 | ✅ |
| 손끝·팜 접촉 플래그 | 6 | **SDK `get_fingertip_sensor_data()`** | ✅ |
| 손끝 위치(물체 기준) | 15 | URDF 순기구학 × 물체 자세 | ⚠️ 물체 자세 필요 |
| **물체 상대위치·속도·각속도·상승높이** | **10** | **비전(3D 자세 추정)** | ❌ **없음** |
| 과제 진행 상태 | 7 | 위 값에서 파생 | ⚠️ 파생 |

**핑거팁 FT·촉각 센서가 실재하므로 접촉 관찰은 실물에서 확보된다.** 어제 최대 리스크로
잡았던 "접촉 센싱 불가 → obs48 재학습" 분기는 소멸했다. 남은 단일 블로커는
**물체 6D 자세(직접 10칸, 파생 22칸)** 이고, 저장소에 카메라 수신 경로가 없다.

## 3. 시뮬레이터 이관 전략 — 재학습은 피할 수 없다

**전제를 분명히 한다: 현재 GraspLift 정책 가중치는 MuJoCo로 이관되지 않는다.**
파지는 전적으로 접촉 현상이고 Unity PhysX와 MuJoCo의 접촉 모델이 다르므로,
물리를 바꾸면 재학습이 필요하다. 기존 가중치는 최대 `--initialize-from` 시드
수준이며 배포 산출물로는 못 쓴다.

그래도 MuJoCo로 가는 게 맞다고 본다: 이 저장소의 이력 자체가 Unity 물리와 싸운
기록이다(`DEBUG_OSCILLATION_*.md`, badInertia 함정, 드라이브 게인 10000/200/100000
수동 튜닝, 손가락이 서로 지나쳐 그립이 다시 벌어지는 기하 문제). 접촉 리치 과제에서
MuJoCo의 접촉 모델은 sim2real 갭을 줄이는 쪽으로 작동한다.

**재학습해도 살아남는 자산** — 이게 프로젝트의 진짜 가치다:
- `Dg5fGraspLiftSpec`에 축적된 **보상 설계 지식**(왜 closure가 0.75에서 포화하는지,
  왜 COM을 낮춰야 하는지, 왜 potential-based new-best 델타여야 하는지, 왜 topple을
  종료 조건으로 넣어야 하는지 — 전부 실측 근거가 주석에 남아 있음)
- URDF·메시, 안전 봉투(`ArmSafeMinDeg/MaxDeg`)
- Phase 1의 실물 배선(관절 대응표, RTDE, SDK 센서) 전부
- 비전 파이프라인 골격

### MuJoCo Unity 플러그인이 하는 일 (공식 문서 확인)

플러그인은 Unity를 시각화로 격하시키는 것이 아니라 **물리 소유권만 MuJoCo에 넘긴다**:

- **MuJoCo**: 물리(동역학·접촉·적분)
- **Unity**: 에셋·렌더링, 게임 로직, 시뮬레이션 시간(Fixed Timestep), 중력 설정

MJCF를 에디터로 임포트하면 **MJCF 요소 ↔ Unity 컴포넌트가 1:1 대응**하는 계층이
생성된다(`MjBody`/`MjGeom`/`MjJoint`/`MjSite`/`MjSensor`/`MjActuator`, 게임오브젝트당
MuJoCo 컴포넌트 최대 1개). **`MjScene` 하나**가 계층을 스캔해 통합 MJCF를 만들고
컴파일한 뒤 각 컴포넌트를 런타임 데이터에 인덱스로 바인딩하며,
`MjScene.FixedUpdate()`가 물리 스텝 후 GameObject transform을 동기화한다.

따라서 **Unity가 ML-Agents 에이전트 로직을 계속 소유하면서 물리만 MuJoCo에 넘기는
것이 플러그인의 정상 사용법**이다.

#### 우리 코드에 직접 영향하는 제약

1. **트리거 콜라이더 미지원 — 문서가 "터치 센서를 쓰라"고 명시.** 접촉 센서 3종
   (`GraspLiftObjectContactSensor`/`GraspLiftSurfaceContactSensor`/
   `GraspLiftHandSurfaceSensor`)이 Unity 충돌 콜백 기반이라 `MjSensor` 터치로
   전면 재작성해야 한다. 다만 이는 **실물 핑거팁 FT 센서와 대응이 좋아지는** 방향이다.
2. **동적 씬 편집 미지원 — 컴포넌트 추가/제거는 전체 씬 재생성(비쌈).**
   물체 **위치** 랜덤화는 qpos라 싸지만, `block_width`/`block_height`를 에피소드마다
   바꾸는 현재 커리큘럼은 geom 크기 변경 = 재컴파일이라 비싸다. → 런 단위 고정 또는
   병렬 영역별 크기 배치로 **설계를 바꿔야 한다.**
3. **`MjScene`은 하나** — 학습영역 20개가 한 모델로 컴파일돼 한 번의 스텝으로 돈다.
   기능상 문제는 없으나 **처리량은 실측 대상**이다.

### 학습 실행 위치: 두 안 (미결 — 벤치마크로 판정)

| | A: Unity + MuJoCo 플러그인 + ML-Agents | B: Python MuJoCo 학습 + Unity 시각화 |
|---|---|---|
| 보상 코드 | **C# 그대로 유지** | Python 포팅 필요 (수치 드리프트 위험) |
| ML-Agents 툴링·ONNX 익스포트 | **검증된 경로 보존** | 새로 구축 |
| 접촉 센싱 | `MjSensor` 터치로 재작성 | MuJoCo 네이티브 |
| 병렬 처리량 | **미측정** (단일 `MjScene`이 20영역을 한 스텝에) | CPU 코어 병렬, 필요시 MJX |
| 크기 랜덤화 | 재컴파일 비용 → 설계 변경 필요 | 자유 |
| 선례 | ML-Agents 연동은 공식 문서에 명시, 튜토리얼 존재 — 단 **카트폴 수준**이고 "early development", 관찰/액션 배선·병렬·처리량은 미다룸 | 표준 경로 |

**아직 결정하지 않는다.** A는 보상 C#·ML-Agents 툴링·ONNX 경로를 모두 보존하므로
이관 비용이 B보다 작을 수 있고, 접촉도 터치 센서라는 깔끔한 대체 수단이 있다.
남는 쟁점은 **①단일 `MjScene`으로 20영역 처리량 ②크기 랜덤화 재컴파일 비용
③플러그인의 Unity 6000.4 지원 여부**이며, 전부 추측이 아니라 측정으로 답할 문제다.
→ **Phase 0에 스파이크(spike) 과제로 넣고 그 결과로 A/B를 확정한다.**

## 4. Phase 0 — 스펙 확정 & 모델 정본화 (선행 차단 요소)

### 즉시 확인해야 하는 것

- **DG5F-M의 정체** — 저장소 URDF는 `dg5f_{left,right}{,_short}.urdf` 4종이고 SDK 모델
  코드는 `5f`(0x5F12/22) / `5f_s`(0x5F14/24) / `5f_s15`(0x5F34/44)다. **"M"이 어디에
  대응하는지 불명.** 그리고 **좌/우손 확정이 필수**다 — 정책은 `LeftFistDeg`(왼손)로
  학습됐고, 실물이 오른손이면 미러 변환이 들어간다. MJCF 모델의 정본이 여기서 갈린다.
- **UR5e**: Polyscope 버전, 네트워크(IP), RTDE 활성화 여부.

### 스펙 요구 목록 (미정 항목)

**이동 베이스** — Nav2가 요구하는 것: 구동 방식(차동/전방향), 오도메트리 출력(엔코더),
LiDAR 모델, **ROS2 드라이버 제공 여부**, 적재 하중(UR5e+DG5F 무게 지지), 풋프린트,
배터리, 비상정지 경로.

**웨이퍼 케이스** — 치수, 질량, **파지 지점(손잡이/엣지/플랜지)**, 재질·마찰,
**허용 기울기·가속 한계**, 청정도 요구.

### 모델 정본화

`urdf/ur5e_dg5f_build/ur5e_dg5f_left.urdf`(기존 결합 산출물, 링크 41 / revolute 26) →
**MJCF 변환**. 이후 MuJoCo 학습과 Unity 시각화가 **같은 MJCF 하나**를 참조한다.
MJCF는 A/B 어느 안을 골라도 필요하다(플러그인도 MJCF를 소비한다) — 즉 공통 비용이다.

MuJoCo가 URDF를 직접 컴파일할 수 있어 출발점은 자동이지만, URDF에 없어서 **손으로
추가해야 하는 것**:

- **액추에이터** — 26관절 position 서보. Unity xDrive 게인(10000/200/100000)에
  대응하는 kp/kv 재튜닝
- **터치 센서** — 핑거팁·팜. MuJoCo 네이티브이고 실물 FT 센서와 1:1 대응
- **자기충돌 제외 쌍** — Unity `RobotSelfCollisionIgnore`의 지식이 그대로 이전
- **마찰·솔버 파라미터**(solref/solimp) — MuJoCo로 가는 이유 자체
- **관성 누락 링크 패치** — WORKLOG §22의 그 문제가 재발한다. UR 더미 링크 5개
  (`base_link`/`base`/`flange`/`tool0`/`ft_frame`)에 inertial이 없어 Unity에서
  mass 0.1 / 관성 1e-4로 메웠고, MJCF에서도 같은 패치가 필요하다
  (MuJoCo는 관절 달린 질량 0 바디를 거부한다)
- **대상 물체** — 블록(지금) / 웨이퍼 케이스(나중), 질량·COM·마찰 포함

메시 현황: **충돌 메시는 전부 STL**로 MuJoCo 네이티브 지원. **시각 메시 35개가 DAE**
인데 MuJoCo는 DAE를 지원하지 않으므로 ①DAE→OBJ 변환 ②시각용으로 충돌 STL 재사용
③Unity가 기존 임포트 프리팹을 렌더링하고 MuJoCo 상태만 받아 배치 — 중 택일.
③은 기존 Unity 시각 자산(`Assets/Robots/Prefabs/`, 구동설정 완료)을 살리지만
플러그인 표준 사용법에서는 벗어난다.

### 스파이크 과제 — A/B 확정용 (측정으로만 답이 나온다)

1. **플러그인 × Unity 6000.4 호환** — 튜토리얼 기준은 >2021.2.19f다. 우리 에디터에서
   임포트·스텝이 도는지부터 확인.
2. **처리량** — 단일 `MjScene`에 학습영역 20개를 올려 스텝 레이트 측정.
   현재 Unity PhysX 구성과 비교.
3. **크기 랜덤화 비용** — geom 크기 변경 시 씬 재생성 실측. 비싸면 커리큘럼을
   런 단위 고정 또는 영역별 배치로 재설계.

## 5. Phase 1 — 실물 구동·센싱 경로 (MuJoCo와 무관, 지금 착수 가능)

**이 단계를 MuJoCo 이관보다 먼저 하는 이유가 두 가지다.** ①MuJoCo 재학습에는 시간이
걸리는데 그 전에 실물 배선을 다 검증해두면 새 정책이 나왔을 때 갈아끼우기만 하면 된다.
②여기서 얻는 실측(마찰, 추종 오차, 센서 노이즈, 지연)이 **MuJoCo 모델 캘리브레이션과
도메인 랜덤화 범위의 입력**이 된다. 순서를 뒤집으면 랜덤화를 추측으로 하게 된다.

1. **공식 `dgsdk` 패키지로 브리지 이관** — 현재 ctypes DLL 직접 호출을 교체.
   센서·상태 API가 한꺼번에 열리고 리눅스 실행도 가능해진다(ROS2/WSL2 통합에 필요).
2. **관절 대응표 확정 (안전 필수)** — `JOINT_ORDER`/`JOINT_SIGN`/`JOINT_OFFSET_DEG`가
   여전히 "미검증"이다. `--pose`로 한 관절씩 소각도 주입해 확정하고 표로 남긴다.
   틀린 채로 `MoveServoJoint`를 보내면 손가락이 리밋 방향으로 꺾인다.
3. **핑거팁 센서 실측** — `get_fingertip_sensor_data()` 신호 특성 파악, 접촉 플래그
   6개로 바꿀 **임계값 결정**. sim의 불리언 접촉과 실물 연속 FT값 사이의 변환 정의.
4. **`get_gripper_data()` 로깅** — 관절 실제값·전류·에러코드. 명령 대비 추종 오차를
   측정해 MuJoCo 액추에이터 모델에 반영.
5. **UR5e RTDE 연결** — `getActualQ`/`getActualQd`, 10 Hz `servoJ`. `ArmLinks` 순서가
   UR `q` 순서와 1:1인지, **부호·영점**이 URDF와 맞는지 대조. 여기가 틀리면 관찰
   정규화가 조용히 어긋난다.
6. **ArUco 마커로 물체 자세 공급** — 비전 파이프라인 없이 obs의 비전 의존 10칸을 채우는
   우회로. 마커/지그로 물체 자세를 주면 **비전 개발 전에 파지 루프 전체를 실물에서
   닫을 수 있다.**

**완료 기준**: 기존 Unity 학습 ONNX를 그대로 써서, ArUco로 자세를 공급한 상태에서
실물 UR5e+DG5F가 12 cm 블록을 파지·들어올린다. (성공률은 기대하지 않는다 —
랜덤화 없이 학습된 정책이라 실패해도 정상이다. **검증 대상은 배선과 관찰 조립이
맞는지**이며, 실패 모드 자체가 Phase 2 랜덤화 설계의 데이터다.)

## 6. Phase 2 — MuJoCo 이관 + 재학습 (블록 유지, 포트 검증 게이트)

과제를 바꾸지 않고 **같은 12 cm 블록으로** 재학습한다. 기존 Unity 베이스라인
(학습조건 99.75% / 균일밀도 99.24%)이 있으므로 **비교 가능한 성공률 도달을
포트 검증 게이트로 쓴다.** 과제와 물리를 동시에 바꾸면 무엇이 깨졌는지 알 수 없다.

1. MJCF 물리 파라미터를 Phase 1 실측으로 캘리브레이션
2. 보상·스펙 이관 — 안 A면 C# 유지 + 물리 접근/접촉 센싱만 `Mj*` API로 재작성,
   안 B면 Python 포팅 + 기존 C# 테스트와 **수치 패리티 단위 테스트**
3. 도메인 랜덤화를 **처음부터 설계에 포함** — Unity 환경의 최대 약점이 랜덤화 부재였다.
   Phase 1에서 **측정한 실제 노이즈 크기**를 범위로 쓴다:
   물체 자세 관측 노이즈·지연(최우선), 마찰, 질량, 액추에이터 지연·추종오차, 백래시
4. 짧은 주기 체크포인트 평가 후 조기 중단. 긴 blind run 금지(단일 GPU)

## 7. Phase 3 — Unity 시각화

플러그인으로 **같은 MJCF**를 로드한다. 물리 소유권은 항상 MuJoCo다.

- **안 A를 택했다면** 이 단계는 Phase 2에 흡수된다 — 학습 씬이 곧 시각화 씬이다.
- **안 B를 택했다면** Unity는 학습 루프 밖에서 롤아웃 재생 전용이 된다.

어느 쪽이든 기존 Unity PhysX 학습 경로(`training/scripts/*` 중 GraspLift 계열,
`unity/Assets/MLAgents/GraspLift`)는 **레거시로 동결하고 삭제하지 않는다** —
Phase 2 게이트의 비교 기준(99.75%)이기 때문이다.

## 8. Phase 4 — 웨이퍼 케이스 재타겟 + Pick & Place

스펙 도착 후 착수. 기존 과제는 "파지+들어올려 유지"까지이고 **place가 없다** —
새 기능이다.

**분업을 권장한다: 파지는 RL, 이송·배치는 스크립트/플래너.**
- 파지는 접촉 리치라 스크립트로 짜기 어렵다 → RL의 몫
- 배치는 기하 문제이고 **정밀도·기울기·가속 제약 준수를 검증해야** 한다 →
  결정적 플래너가 훨씬 신뢰할 수 있고, 웨이퍼 취급 제약을 명시적으로 걸 수 있다

스펙에 따라 연쇄 변경되는 것: 물체 치수·질량·COM, `GraspTargetHeightOffset`,
**`LeftFistDeg` 파지 포즈 전면 재설계**(FOUP류는 5지 감싸쥐기가 아니라 손잡이/엣지
그립이 표준 → 접촉 대향각 90° 조건과 케이지 판정도 함께), `ToppleLimitDegrees`
(현재 45°, 웨이퍼는 훨씬 엄격할 것), YOLOv8 재학습.

## 9. Phase 5 — 자율주행 (Nav2)

- **토폴로지**: ROS2 + Nav2 + slam_toolbox를 **WSL2(Ubuntu) 또는 Docker**에서,
  Unity는 Windows에서, 둘을 **ROS-TCP-Connector/Endpoint**로 연결. ROS2를 Windows
  네이티브로 돌리는 건 피한다.
- **호환 작업 예상**: Robotics-Nav2-SLAM-Example은 Unity 2020.3 LTS / ROS2 Foxy~Galactic
  시절 기준이다. 이 프로젝트는 **Unity 6000.4.0f1**이라 ROS-TCP-Connector 패키지 버전,
  렌더 파이프라인(이 프로젝트는 Built-in), 예제 로봇·센서 프리팹에 손이 필요하다.
- **베이스 스펙 대기 중에도 착수 가능** — 예제의 스톡 로봇으로 Nav2/SLAM 파이프라인을
  먼저 세우고, 실 베이스 스펙이 오면 교체한다. 스펙 대기로 막혔을 때 돌릴 작업.

## 10. Phase 6 — 통합 오케스트레이션

순차 상태기계: `NAVIGATE → STOP → LOCALIZE → PICK → (NAVIGATE) → PLACE`

**미들웨어 경계 권장안**: ROS2는 **주행과 상위 오케스트레이션**에만 쓰고,
매니퓰레이션 **10 Hz 내부 루프는 RTDE+dgsdk 직결**로 유지한다. `pick`/`place`를
ROS2 액션으로 노출해 상태기계가 호출하는 구조. 이유는 결정론적 제어 루프를 DDS에
태우면 지연·지터 관리가 추가 부담이 되고, 순차 동작이라 주행과 파지가 실시간으로
결합될 필요가 없기 때문이다. (Tesollo도 ROS2 패키지를 제공하므로 전면 ROS2 통합도
가능하지만, 1인 체제에서는 위 절충이 낫다고 본다.)
