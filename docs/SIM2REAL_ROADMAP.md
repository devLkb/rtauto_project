# Sim2Real 로드맵 — DG5FGraspLift → 실물

작성 2026-08-25. 1인 풀타임·로컬 단독 머신(RTX 2080) 체제 기준.
현재 활성 정책 계약은 [`DG5F_GRASP_LIFT.md`](DG5F_GRASP_LIFT.md), 이 문서는 그 정책을
실물 하드웨어로 옮기는 순서만 다룬다.

## 0. 전제

| 항목 | 현재 상태 |
|---|---|
| 활성 정책 | `DG5FGraspLift` spec 1.0.0, obs 57 / act 7, 결정주기 0.1 s (10 Hz) |
| 대상 물체 | 0.035 × 0.035 × 0.12 m 사각기둥, 밀도 1800 kg/m³ (~0.265 kg), COM 높이비 0.20 |
| 성공 조건 | 3접촉 이상 + 대향각 90° 이상 + 케이지 안 + 0.3 s 유지 → 0.10 m 들어올려 0.5 s 유지 |
| 하드웨어 | UR5e 팔 6관절 + Tesollo DG5F 5지 손 20관절 (+ 이동 베이스, 보류) |
| 최종 목표 물체 | 반도체 웨이퍼 운반 상자 — **스펙 미정** |
| 구세대 환경 | `Grasp`(파지만) / `Reach`(팔 이동만) 삭제 완료. GraspLift가 유일 |

## 1. 핵심 판단 — 병목은 구동이 아니라 지각이다

계약을 슬롯 단위로 뜯어보면 sim2real 난이도가 어디 있는지 분명해진다.

### 액션 7 — 실물 이관이 쉬운 쪽

`Dg5fGraspLiftAgent.OnActionReceived` / `ApplyArmTargets` / `ApplyGripTargets`:

- `[0..5]` 팔: 관절 **각도 델타**를 누적해 `_armTargetDeg`에 절대 목표각으로 clamp
  (`ArmSafeMinDeg`/`ArmSafeMaxDeg`) → xDrive 위치 목표.
  **관절공간 위치 제어라 IK가 필요 없고 UR RTDE로 그대로 명령 가능하다.**
- `[6]` 그립: 스칼라 `_closure` ∈ [0,1] → 20관절을
  `Mathf.Lerp(_openHandDeg[i], LeftFistDeg[i], closure)` 로 펼침.
  **결정적(deterministic) 고정 매핑**이라 Python으로 그대로 이식 가능하고,
  결과 20개 각도는 기존 `vision/dg5f/dg5f_sdk_bridge.py`가 이미 받는 형식이다.

즉 구동 경로는 양쪽 다 이미 열려 있다. 10 Hz는 실시간 여유도 충분하다.

### 관찰 57 — 실물에 존재하지 않는 쪽

| 슬롯 | 내용 | 실물 확보 가능성 |
|---|---|---|
| 0..5 | 팔 관절각 (정규화) | ✅ UR RTDE `getActualQ()` |
| 6..11 | 팔 관절속도 (÷π) | ✅ UR RTDE `getActualQd()` |
| 12 | 그립 폐쇄도 | ✅ 우리가 명령한 값 |
| 13..21 | **물체** 파지목표 오프셋 3 + 선속도 3 + 각속도 3 (베이스 좌표) | ❌ 비전 필수 |
| 22 | 물체 스폰 대비 수직 변위 | ❌ 비전 필수 |
| 23..37 | 손끝 5개의 물체 상대위치 (팜 좌표, 15) | ⚠️ 손 FK(가능) × 물체 포즈(비전) |
| 38..42 | 손끝 접촉 플래그 5 | ❌ **접촉 센싱 없음** |
| 43..48 | 명령된 팔 목표각 | ✅ 내부 추적 |
| 49..50 | 팜 접촉 플래그, 접촉수/6 | ❌ 접촉 센싱 없음 |
| 51..52 | 파지 진행도, 파지 확정 플래그 | ❌ 접촉에서 파생 |
| 53..55 | 들어올림 진행도, 유지 진행도, 파지거리 | ❌ 비전 필수 |
| 56 | 에피소드 경과 | ✅ 내부 |

**57칸 중 공짜로 얻는 건 14칸(팔 상태·명령·폐쇄도·시간)뿐이고, 나머지 43칸은
전부 ①물체 6D 포즈(비전) 또는 ②접촉 센싱에 의존한다.** 그리고 지금 이 저장소에
그 둘은 존재하지 않는다 — hand-eye 캘리브레이션 없음, DG5F에 촉각 센서 없음.

따라서 로드맵은 "하드웨어를 연결한다"가 아니라 **"관찰 벡터를 실물에서 어떻게
채우느냐"**를 중심으로 짜야 한다.

## 2. Phase 1 — 구동 경로 검증 (관찰 없이, 열린 루프)

지각 문제를 건드리기 전에 모터 경로만 격리해서 증명한다. 나중에 실패했을 때
원인이 정책이냐 배선이냐를 가르기 위한 기준선이다.

1. **UR5e RTDE 연결** — `ur_rtde`로 `getActualQ`/`getActualQd` 읽기, 10 Hz `servoJ` 명령.
   ROS2는 혼자 새로 배우며 쓰기엔 비용이 커서 RTDE 직결을 택한다.
2. **관절 규약 대조** — `Dg5fGraspLiftSpec.ArmLinks` 순서(shoulder→upper_arm→forearm→
   wrist_1→wrist_2→wrist_3)가 UR 컨트롤러 `q` 순서와 1:1인지, **부호와 영점**이 URDF와
   일치하는지 확인. `ArmSafeMinDeg`/`MaxDeg`는 정규화 분모이기도 해서 여기가 틀리면
   관찰값 전체가 조용히 어긋난다.
3. **DG5F 관절 매핑 확정** — `dg5f_sdk_bridge.py`의 `JOINT_ORDER`/`JOINT_SIGN`/
   `JOINT_OFFSET_DEG`는 파일 주석에 **"미검증"**으로 명시돼 있다. `--pose`로 한 관절씩
   보내 실측 확정하고 상수를 고정한다.
4. **closure→20관절 lerp 이식** — `ApplyGripTargets`의 lerp를 Python으로 옮겨
   closure 0 / 0.25 / 0.5 / 0.75에서 실물 손 모양이 sim과 같은지 대조.
   `EffectiveGripClosure`=0.75 이상에서 손가락이 서로 지나쳐 **다시 벌어지는** 특성까지
   재현되는지 확인(스펙에 실측 근거 있음: 0.75에서 3.1~3.6 cm, 1.0에서 6.3 cm).
5. **좌/우손 확인** — 정책은 `LeftFistDeg`(왼손)로 학습됐다. 실물이 오른손이면
   브리지 `--unmirror`를 쓴다.

**완료 기준**: sim에서 성공한 에피소드의 act7 시퀀스를 녹화 → 실물에서 재생 →
같은 궤적이 나온다. 물체 없이 먼저, 그 다음 물체를 놓고.

## 3. Phase 2 — 관찰 경로 구축 (진짜 병목)

1. **Hand-eye 캘리브레이션** — ZED ↔ UR5e 베이스 외부 캘리브레이션. 현재 없음. 필수.
   정책이 기대하는 좌표계는 로봇 베이스 프레임이다.
2. **물체 6D 포즈 10 Hz** — 지금 `zed_object_detection`은 YOLOv8 검출 + 중심 깊이까지다.
   슬롯 13..21은 **각속도**까지 요구하므로 **자세(orientation)** 추정이 필요하다.
3. **속도·각속도** — 포즈 유한차분 + 필터링. 비전 노이즈가 속도로 증폭되는 구간이라
   필터 설계가 성능을 좌우한다.
4. **접촉 센싱 조사 (분기점)** — DG5F SDK가 실제로 무엇을 읽을 수 있는지 확인
   (관절 전류? 위치 오차? 힘?). 결과에 따라 로드맵이 갈린다:
   - 접촉 근사가 가능하면 → 전류/위치오차 임계로 6개 플래그 대체, obs57 유지
   - 불가능하면 → **접촉 의존 슬롯 9개(38..42, 49..52)를 뺀 obs48 정책으로 재학습.**
     사소한 수정이 아니라 정책을 새로 학습하는 일이므로 일정에 반영해야 한다.
5. **손끝 위치 FK** — 20관절 각도 + URDF로 계산 가능(비전 불필요).
6. **추론 아키텍처: Unity를 실시간 루프에서 뺀다** — ONNX는 obs57→act7 순수 함수이므로
   Python `onnxruntime`에서 추론하고, Unity는 **학습 시뮬레이터 전용**으로 남긴다.
   Python이 이미 DG5F 브리지를 소유하고 UR RTDE도 갖게 되므로 경로가 하나로 모인다.
   (참고: 이전 ZED→Unity 수신기 `CameraTargetReceiver.cs`는 삭제됐다. 이 결정에 따라
   되살릴 필요가 없다.)

**완료 기준**: 실물에서 obs57(또는 obs48)을 10 Hz로 구성해 로깅하고, sim의 관찰 분포와
슬롯별로 대조한다. **이게 sim2real 갭을 정량화하는 유일한 방법이다.**

## 4. Phase 3 — 폐루프 실행 + 반응형 도메인 랜덤화

- 안전장치 먼저: 관절 속도 상한, 워크스페이스 경계, 슬루 리밋, 즉시 정지 경로.
  브리지의 `--max-step`(틱당 2°) 같은 기존 장치를 팔에도 둔다.
- **랜덤화는 선제적으로 넓게 깔지 않는다.** 현재 GraspLift 환경의 랜덤화는 사실상
  스폰 위치/방위 + `block_width`/`block_height`/`block_com_height_fraction` 파라미터뿐이다.
  로컬 단일 GPU로 모든 물리 축을 미리 스윕할 시간이 없으므로,
  **실패 모드를 관찰한 뒤 그 축만 좁게 추가**하고 재학습한다.
- 우선순위 후보: ①물체 포즈 관측 노이즈(비전 오차를 sim에 주입 — 가장 직접적),
  ②질량·마찰, ③액추에이터 지연/추종 오차, ④관절 백래시.
- 긴 blind run 금지. 짧은 주기로 체크포인트 평가 후 조기 중단/재조정.

**완료 기준**: 실물 12 cm 블록 파지 + 0.10 m 들어올림 + 유지.

## 5. Phase 4 — 웨이퍼 박스 재타겟 (스펙 확정 후)

**먼저 받아야 할 스펙**: 치수, 질량, 파지 지점(손잡이/엣지/플랜지), 재질·마찰,
취급 제약(허용 기울기, 가속 한계, 청정도).

스펙이 오면 아래가 연쇄 변경된다 — 메시 교체 수준이 아니다:

- `BlockWidth`/`BlockHeight`/`BlockDensity`/`BlockComHeightFraction` → 새 오브젝트
- `GraspTargetHeightOffset` 재계산 (현재는 상단면 2 cm 아래를 겨냥)
- **`LeftFistDeg` 파지 포즈 재설계** — 웨이퍼 캐리어(FOUP류)는 5지 감싸쥐기가 아니라
  손잡이/엣지 그립이 표준이다. 그러면 `EffectiveGripClosure` 특성, 접촉 대향각 90° 조건,
  케이지 판정(`GraspCenterMaxDistance`)까지 다시 설계해야 한다.
- `ToppleLimitDegrees`(현재 45°) — 웨이퍼 취급은 기울기 제약이 훨씬 엄격할 가능성이 높다.
- YOLOv8 재학습 + 새 오브젝트 포즈 추정

Phase 1~3에서 만든 자산(관절 매핑, RTDE 경로, 캘리브레이션, 관찰 파이프라인,
랜덤화 루프)은 **전부 재사용**된다. 재학습되는 건 정책 자체다.

## 6. Phase 5 — 이동 베이스 (보류)

지금은 설계도 하지 않는다. 착수 시 원칙만 기록:

- **주행을 RL로 풀지 않는다.** 기성 내비게이션 스택(ROS2 Nav2 등)을 쓰고
  매니퓰레이션 정책과 분리한다. 혼자서 이동+파지 모놀리식 정책을 디버깅하는 건 비현실적이다.
- 인터페이스는 순차 실행: 베이스가 목표 근처로 이동 → **정지** → 팔 정책 실행.
  모바일 매니퓰레이션 동시 제어는 범위 밖.

## 7. 상시 제약

- **단일 GPU 시분할** — 학습(야간/오프타임) ↔ 하드웨어·비전 작업(주간)을 시간대로 분리.
  Unity 학습 + ZED YOLO 추론 동시 실행은 8 GB VRAM 한계에 걸린다.
- **하드코딩 금지** — IP/포트/경로는 `config/rtauto_config.py`(+ `.env`)가 유일한 출처.
  캘리브레이션·관절 오프셋 같은 물리 상수는 정본 파일 하나에만 두고 복제하지 않는다.
