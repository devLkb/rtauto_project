# 손끝 센서 없이 "잡았다" 를 알아내기 — 설계 정본

**만든 날**: 2026-09-17 / **상태**: 설계·코드 완료, **실물 검증 0회**

---

## 0. 한 줄 요약

우리 손에는 손끝 센서가 없다. 그래서 **모터 전류 + 시킨 각도와 실제 각도의 차이 +
관절 속도** 세 가지를 합쳐 "닿았다" 를 추정하고, 들어올린 뒤 **일부러 조금 더 조여 봐서**
"아직 쥐고 있다" 를 확인한다.

> 🛑 **아래 숫자 중 실물에서 잰 것은 하나도 없다.** 전부 잠정값이고, 첫 단계는
> `hand/measure_baseline.py` 로 **무부하 전류를 재는 것**이다. 그 표가 없으면
> 코드가 시작 자체를 거부한다.

---

## 1. 왜 필요한가

`CLAUDE.md` 하드웨어 표: **DG-5F-M-R 에는 손끝 힘·촉감 센서가 없다.** 구매 옵션이었고
사지 않았으며 비용 때문에 앞으로도 사지 않는다(2026-09-14). SDK 에 손끝 센서 함수가
있어도(`CallbackForOnReceivedFingertipSensorData`) 값은 들어오지 않는다.

그래서 **읽을 수 있는 것만으로** 다음 두 가지를 알아내야 한다:

1. 손가락이 물체에 **닿았는가** → 언제 조이기를 멈출지
2. 들어올린 뒤에도 **쥐고 있는가** → 다음 동작으로 갈지, 다시 잡을지

---

## 2. 읽을 수 있는 것 — 확인된 사실

`vision/dg5f/vendor/dgsdk-python/libs/DGDataTypes.h` 의 `ReceivedGripperData` 주석에서
확인했다(추측이 아니다):

| 들어오는 것 | 단위 | 개수 | 쓰임 |
|---|---|---|---|
| `joint` | 도(degree) | 20 | 실제 각도 |
| `current` | **mA** | 20 | 모터 전류 |
| `velocity` | **rpm** | 20 | 관절 속도 |
| `temperature` | °C | 20 | 과열 보호 |
| `TCP` | mm / 도 | 30 | 손끝 좌표 |
| `moduleErrorCode` | — | 1 | 고장 코드 |
| `controlPeriod` | — | 1 | 통신 주기 |

**⚠️ 지금 브리지는 속도를 안 받고 있다.** `vision/dg5f/dg5f_sdk_bridge_dgsdk.py` 의
`RECEIVED_DATA_TYPE = [1, 2, 7, 0, ...]` 은 각도(1)·전류(2)·고장코드(7)만 켜 두었다.
속도(4)를 켜지 않으면 **0 만 들어온다.** `hand/measure_baseline.py` 의 `RealHand` 는
`[1, 2, 4, 7, ...]` 로 켜서 붙는다.

### 쓸 수 있지만 아직 안 쓰는 것

SDK 에 `SetCurrentControlMode` / `SetTargetCurrent*` / `SetTorqueLimitMode` /
`SetGraspData(graspMode, graspForce, ...)` 가 있다. 즉 **전류 자체를 제한하며 쥐는 것**도
가능하다. 지금 설계는 위치로 명령하고 전류를 **읽기만** 하는데, 무부하 전류를 재고 나면
"전류 상한을 걸고 쥔다" 쪽이 더 안전할 수 있다. **실측 후에 다시 판단한다.**

## 3. 손을 누가 쥐고 있나 — 먼저 정해야 하는 것

🛑 **이 그리퍼는 TCP 연결을 딱 하나만 받는다.** 2026-08-31 실물 실측으로, 개발자모드
자체 프로토콜과 사용자모드 Modbus TCP **둘 다** 동시 접속이 안 됐다(근거:
`vision/dg5f/dg5f_modbus_readback.py` 머리말 — 프로토콜·제어모드와 무관하다).

따라서 로봇 티치펜던트의 URCap 이나 DGManager 가 손을 잡고 있으면 **PC 는 전류를 못
읽는다.** 구성은 하나뿐이다:

```
손:  PC ──DGSDK(개발자모드)──> DG-5F 그리퍼     ← 각도·전류·속도를 여기서 읽는다
팔:  PC ──ur_rtde──────────> UR16e 컨트롤박스   ← 팔만 담당
```

## 4. "닿았다" 를 어떻게 판단하는가

### 4-1. 세 가지를 **모두** 만족해야 한다

```
갈 길이 남았는데(각도 오차)  +  안 가고 있고(속도 ≈ 0)  +  힘은 쓰고 있다(전류 ↑)
```

| 조건 | 설정 키 | 잠정값 |
|---|---|---|
| 전류가 무부하 기준보다 높다 | `DG5F_CONTACT_CURRENT_SIGMA` / `..._FLOOR_MA` | 흔들림의 6배, 최소 80 mA |
| 시킨 각도까지 못 갔다 | `DG5F_CONTACT_POS_ERR_DEG` | 2.0도 |
| 거의 멈췄다 | `DG5F_CONTACT_VEL_RPM` | 3.0 rpm |
| 위가 **연속으로** 유지된다 | `DG5F_CONTACT_HOLD_TICKS` | 8번 (≈40 ms) |

### 4-2. 가장 중요한 한 가지 — "각도 오차" 는 뺄 수 없다

**시킨 각도까지 다 가서 멈춘 관절도 속도가 0 이고 전류가 낮다.** 이걸 접촉으로 세면
**아무것도 안 잡고도 "잡았다" 가 나온다.**

멈춰 있고 오차도 없는 것은 접촉의 **반대**다. 그래서 세 조건 중 각도 오차만은 선택이
아니다. 이것 하나로 가장 위험한 오판이 막힌다
(시험: `test_시킨각도에_도달해_멈춘_관절은_접촉이_아니다`).

### 4-3. 왜 "한 번 넘었다" 로 안 믿는가

전류는 **방향이 바뀔 때도 튄다.** 순간값으로 판정하면 물체가 없는데도 켜진다. 그래서
연속으로 유지될 때만 확정한다.

### 4-4. 한 번 닿으면 유지한다

조이기를 멈추면 전류가 다시 내려간다. 그때 "안 닿았다" 로 되돌아가면 **잡고 있는데
놓쳤다고 판단**해 버린다. 되돌리는 것은 `reset()` 으로 명시적으로만 한다.

### 4-5. 손가락 수로 센다

관절 20개는 손가락 5개 × 4개다(`thumb_cmc..pinky_pip`, 채널 순서는
`vision/dg5f/dg5f_sdk_bridge.py` 의 `CHANNEL_NAMES`). 한 손가락의 관절 4개가 다 닿아도
**손가락은 1개**다. `DG5F_CONTACT_MIN_FINGERS`(기본 3개) 이상이면 조이기를 멈춘다 —
시뮬레이터의 성공 기준(`min_tips=3`)과 같은 값에서 시작한다.

## 5. 기준값을 어떻게 정하는가 — **재서** 정한다

### 5-1. 숫자 하나로 못 박으면 안 되는 이유

무부하 전류는 **관절마다 다르고, 같은 관절이라도 각도마다 다르다**(중력·마찰·기구 간섭).
"200 mA 넘으면 접촉" 같은 상수 하나를 쓰면 엄지에서는 늘 켜지고 새끼에서는 절대 안 켜진다.

### 5-2. 그래서 표로 만든다

`hand/measure_baseline.py` 가 **아무것도 안 잡은 채** 천천히 폈다 오므렸다 하며
관절 20개 × 각도 10도 구간마다 **평균과 흔들림**을 재서
`config/dg5f_current_baseline.json` 에 저장한다.

접촉 기준 = `무부하 평균(그 각도) + max(흔들림 × 6, 80 mA)`

- **재 본 적 없는 구간은 양옆에서 빌려 쓰지 않는다** — 없는 것을 있는 척하면 조용히 틀린다.
  그 각도에서는 "판단 못 함" 으로 남긴다.
- 한 구간을 믿으려면 표본 20개 이상(`CurrentBaseline.MIN_SAMPLES`).
- **양 끝 각도에서 잠깐 머문다**(`--dwell`). 안 그러면 다 오므린 자세 — 실제로 가장 많이
  쓰는 구간 — 의 표본이 거의 안 쌓인다. 가짜 손으로 돌려 보다 발견했다.

### 5-3. 재기 전 반드시

- **손 안과 손 주변을 비운다.** 뭔가에 닿은 채로 재면 그 힘이 "평소" 로 들어가
  나중에 진짜 접촉을 못 알아챈다.
- **천천히 움직인다.** 빠르면 가속 때문에 전류가 부풀려져 기준이 실제보다 높게 잡힌다.
- URCap/DGManager 를 먼저 끊는다(§3).

## 6. 순서도

```
준비      손을 벌린 채 시작 자세로
  ↓
닫는 중    관절 목표를 조금씩 오므린다
  ↓        닿은 관절은 **그 자리(+아주 조금)** 에 세워 둔다
쥐고 있음  손가락 3개가 닿으면 더 안 조인다
  ↓
드는 중    팔을 5 cm, 0.02 m/s 로 천천히 올린다
  ↓
확인 중    ① 집어보기 ② 전류 ③ (가능하면) 팔 힘센서
  ↓
성공  /  실패(→ 놓고 다시)
```

구현: `hand/grasp_sequence.py`. 상태는 `Phase` — `READY / CLOSING / HOLDING / LIFTING /
VERIFYING / SUCCESS / FAILED_NO_CONTACT / FAILED_SLIPPED / ABORTED`.

### 6-1. 닿은 관절을 세워 두는 이유

위치로 명령하는 손이라, 닿은 뒤에도 목표를 계속 오므리면 제어기는 차이를 메우려고
**전류를 계속 올린다.** 종이컵 같은 것은 찌그러지고 단단한 것은 손 밖으로 밀려난다.

## 7. 들어올린 뒤 "아직 쥐고 있나" 확인

### 7-1. ① 집어보기 — 일부러 조금 더 조여 본다

**처음 설계는 틀렸다.** "물체가 빠지면 손가락이 더 닫힌다" 로 잡으려 했는데, §6-1 대로
닿은 관절의 목표를 그 자리에 세워 두므로 **물체가 빠져도 손가락이 0.5도쯤밖에 안 움직인다.**
시험을 쓰다가 드러났다.

그래서 가만히 보는 대신 **조금 더 조여 본다**(`GRASP_PROBE_DEG`, 잠정 5도):

- 물체가 있으면 **못 들어간다** → 잡고 있다
- 물체가 없으면 **그만큼 들어간다** → 빈손 (`GRASP_SLIP_CLOSE_DEG`, 잠정 3도 이상 움직이면)

확인이 끝나면 조인 것을 **되돌린다** — 확인하려다 물체를 찌그러뜨리지 않는다.

### 7-2. ② 전류 — 무게를 들고 있으면 유지된다

잡은 직후 대비 전류 합이 `GRASP_SLIP_CURRENT_RATIO`(잠정 50%) 아래로 떨어지면 빈손으로 본다.

### 7-3. ③ 팔의 힘센서 — **가벼운 물체는 못 본다**

UR16e 내장 힘센서로 무게 변화를 본다. 다만 **잡음이 수 N 수준**이라 100 g(≈1 N)짜리는
구분이 안 된다. `GRASP_FT_MIN_DELTA_N`(잠정 3 N) 미만이면 "힘으로는 판단 못 함" 으로
적고 ①②만 쓴다. 과장하지 않는다.

### 7-4. ④ 카메라 — 아직 없다

D405 가 도착하면 "들어올린 뒤 손을 본다" 가 가장 확실한 확인이 된다. 카메라 좌표 맞추기
(Q2)가 선행 조건이다.

## 8. 예외 처리 — 무엇이 생기면 멈추나

| 무슨 일 | 어떻게 아나 | 무엇을 하나 |
|---|---|---|
| 손 고장 | `moduleErrorCode ≠ 0` | 즉시 중단(`ABORTED`) |
| 과열 | `temperature ≥ DG5F_TEMP_LIMIT_C` (65°C) | 즉시 중단 |
| 과전류 | `current ≥ DG5F_CURRENT_LIMIT_MA` (800 mA) | 즉시 중단 |
| 통신 끊김 | 새 상태값이 `DG5F_FRAME_TIMEOUT_S`(0.5초) 동안 안 옴 | 명령 중단 |
| 시간 초과 | `DG5F_CLOSE_TIMEOUT_S`(3초) 안에 손가락 수 미달 | `FAILED_NO_CONTACT` |
| 끝까지 오므림 | 모든 관절이 목표 도달, 손가락 수 미달 | `FAILED_NO_CONTACT` (빈손) |
| 들다가 놓침 | §7 확인 실패 | `FAILED_SLIPPED` |
| 기준표 없음 | `config/dg5f_current_baseline.json` 부재 | **시작 거부** |

## 11. 아직 모르는 것 — 솔직하게

- **무부하 전류가 실제로 얼마인지 모른다.** 위 잠정값이 한 자릿수 틀릴 수도 있다.
- **속도(rpm)가 실제로 들어오는지 확인 못 했다.** 받을 항목에 켜야 한다는 것까지만 확인했다.
- **닿은 뒤 전류가 얼마나 오르는지 모른다.** 그래서 "흔들림의 6배" 가 적당한지 모른다.
- **집어보기 5도가 물체를 찌그러뜨릴지 모른다.** 종이컵 같은 것에서 먼저 확인해야 한다.
- **`SetGraspData` 내장 파지 기능을 안 써 봤다.** 우리가 직접 조이는 것보다 나을 수 있다.
