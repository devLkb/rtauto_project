## 0. 목표 재정의

> **손목에 달린 비전 카메라(eye-in-hand)로 물체를 식별하면, UR16e + DG-5F-M이 스스로
> 움직여 파지점을 찾아내고 물체를 안정적으로 파지한다.**

이 한 문장을 검증 가능한 4개 요건으로 쪼갠다. 이후 모든 설계 판단은 이 표를 근거로 한다.

| # | 요건 | 검증 방법 (충족 판정) |
|---|---|---|
| **R1** | **카메라가 관측의 출처다** | 관찰 벡터의 물체 관련 슬롯이 전부 *추정기 출력*에서 오고, 시뮬레이터 ground truth를 직접 읽는 슬롯이 0개 |
| **R2** | **물체를 식별한다** | 관찰에 물체 종류(클래스)와 6D 자세가 들어가고, 학습 씬에 형상이 다른 물체 2종 이상 + 방해물이 존재 |
| **R3** | **파지점을 스스로 찾는다** | 접근 목표점이 태스크가 준 고정 오프셋이 아니라 정책이 고른 후보. 물체마다 유효 파지 영역이 여러 개 |
| **R4** | **안정적으로 파지한다** | 파지 후 **외란 시험**(흔들기/충격)을 통과해야 성공. 10 cm 들어 0.5초 버티는 것으로는 불충분 |

현행 설계는 **R1~R4를 하나도 만족하지 않는다.** 아래 §1이 그 근거다.

## 1. 현행 설계 진단 — 어디가 어긋나 있나

읽은 대상: `unity/Assets/MLAgents/picknplace/Runtime/Dg5fPicknPlaceSpec.cs`(978줄),
같은 폴더 `Dg5fPicknPlaceAgent.cs`(1156줄), `Editor/PicknPlaceTrainingSceneBuilder.cs`,
`training/config/dg5f_picknplace.yaml`, `training/scripts/picknplace_monitor.py`.

### 1-1. 관찰 57칸 중 25칸이 시뮬레이터 오라클이다 (R1 위반)

`Dg5fPicknPlaceAgent.CollectObservations`의 슬롯 구성:

| 슬롯 | 내용 | 실물 조달처 | 판정 |
|---|---|---|---|
| 0..5 | 팔 관절 각도(정규화) | UR16e RTDE | 가능 |
| 6..11 | 팔 관절 속도 | RTDE | 가능 |
| 12 | 손 닫힘 스칼라 | 우리가 보낸 값 | 가능 |
| **13..15** | **파지목표점 − graspPoint (베이스 좌표)** | **없음** | **오라클** |
| **16..18** | **물체 선속도** | **없음** | **오라클** |
| **19..21** | **물체 각속도** | **없음** | **오라클** |
| **22** | **스폰 대비 물체 상승 높이** | **없음** | **오라클** |
| **23..37** | **손끝 5개 − 물체중심 (팜 좌표)** | 물체 자세 필요 | **오라클 파생** |
| 38..42 | 손끝 접촉 플래그 | dgsdk `get_fingertip_sensor_data()` | 가능 |
| 43..48 | 팔 명령각 | 우리가 보낸 값 | 가능 |
| 49..50 | 팜 접촉 / 접촉 개수 | dgsdk | 가능 |
| 51..56 | 파지·리프트 진행도, 접근 거리, 에피소드 진행도 | 위 오라클에서 파생 | 파생 |

문제의 성격을 정확히 하자. **노이즈가 없다는 게 문제가 아니라, 실물에 존재하지 않는
정보를 정책이 쓰고 있다는 게 문제다.** `cubeTarget.linearVelocity`·`angularVelocity`는
손목 카메라 한 대로 신뢰성 있게 복원되지 않고(모션블러 + 카메라 자체 운동과 물체 운동의
분리 문제), 슬롯 22의 상승높이는 `_spawnObjectHeight` 기준값이라 "에피소드 시작 시점의
물체 높이를 기억하는 시뮬레이터"만 줄 수 있다.

로드맵 §2가 이미 "남은 단일 블로커는 물체 6D 자세(직접 10칸, 파생 22칸)"라고 적어둔 그
지점인데, **지금 코드는 그걸 공짜로 받아쓰고 있어서 학습 중에는 블로커가 드러나지 않는다.**
손목 카메라를 물리적으로 붙이더라도 이 슬롯들이 남아 있으면 카메라는 학습에서 아무
역할도 하지 않는다.

또한 **물체의 회전(orientation)은 관찰에 아예 없다.** 각속도는 있는데 자세는 없다. 대칭
큐브라서 성립하던 전제이며, 손잡이가 달린 대상에는 곧바로 깨진다(로드맵도 동일 지적).

### 1-2. 파지점은 정책이 찾는 게 아니라 상수로 주어진다 (R3 위반)

```csharp
// Dg5fPicknPlaceSpec.cs
public const float GraspTargetHeightOffset = 0.040f;                       // 물체 윗면 위 4cm
public static readonly Vector3 FullHandGraspPointLocalPosition
    = new Vector3(0f, 0.05f, 0.04f);                                       // 팜 로컬 고정
```

접근 보상(`DirectionalApproachPotential`)이 재는 거리는 **"팜에 고정된 한 점"에서 "물체
중심 위 고정 높이의 한 점"까지의 거리**다. 즉 파지점은 태스크가 이미 알려준 단 하나의
정답이고, 정책이 하는 일은 거기까지 가는 것뿐이다. 목표 문장의 "**알아서 파지점을 식별**"에
대응하는 학습 신호가 설계에 존재하지 않는다.

### 1-3. 물체가 한 종류뿐이고 "식별"의 대상이 없다 (R2 위반)

학습 씬에는 큐브 1개만 스폰된다(0.035 × 0.12 m). 커리큘럼이 흔드는 것은 폭·높이·COM
비율뿐이다. 방해물 없음, 클래스 라벨 없음, 형상 다양성 없음. 정책 입장에서 "무엇을 잡을지"는
이미 결정된 문제라 식별할 대상 자체가 없다.

### 1-4. 손이 스칼라 1개다 — 파지 형태를 못 바꾼다 (R3·R4 제약)

`ApplyGripTargets()`는 20개 손가락 관절을 `_openHandDeg ↔ RightFistDeg` 사이에서
**단일 스칼라 `_closure` 하나로 일괄 보간**한다. 파지 형태는 검증된 주먹 자세 하나로
고정이고, 물체 형상이나 파지점에 따라 손 모양을 바꿀 자유도가 없다. 큐브 하나에는
충분했지만(GraspLift에서 실측 검증된 아퍼처 3.1–3.6 cm), 파지점 선택을 학습시키려면
손 자세가 파지점의 함수여야 한다.

### 1-5. top-down 접근이 구조적으로 강제돼 있다 (R3 제약)

`HomeArmDeg = {0, -60, 90, -120, -30, 0}`(팜 30.1° off-vertical)에서 시작해
`TopDownAlignmentPotential`·`GraspPosturePenalty`·`MaximumTopDownAngleDegrees = 35°`가
**top-down 접근만** 보상한다. 옆에서 잡아야 유리한 파지점(손잡이·림)은 구조적으로 학습
불가능하다. 이 항들은 "큐브 top-down"이라는 단일 해법에 정책을 못박는 장치다.

### 1-6. 성공 판정이 "안정적 파지"가 아니다 (R4 위반)

```csharp
IsStableLift   : liftHeight >= CurrentLiftTargetHeight  &&  objectSpeed <= 0.50f
IsLiftComplete : liftHoldSeconds >= CurrentLiftHoldSeconds     // 최종 단계 0.5초
```

0.5 m/s 이하로 10 cm 올려 0.5초 버티면 성공이다. **외란이 전혀 없다.** 손끝 하나에 간신히
걸쳐 미끄러지기 직전인 파지와, 마주보는 3점으로 물린 파지가 같은 점수를 받는다.
force-closure 유사 판정(`IsForceClosureLike`, 대향각 90°)이 있긴 하나 이건 접촉 **방향**만
보는 기하 판정이고 마찰·접촉력·외란 내성을 보지 않는다.

`LiftTiltPenalty`가 2026-08-30에 추가된 경위(해당 주석에 기록됨)가 이 구멍의 증거다 —
아무도 기울기를 벌하지 않으니 정책이 27~34° 기울여 들고 다녔고, 성공률 곡선은 그걸
98~99%로 보고하고 있었다.

### 1-7. 보상이 수동 튜닝된 항들의 더미다 (유지보수 리스크)

한 번의 `OnActionReceived`에서 더해지는 항: `DecisionTimePenalty`,
`DirectionalApproachPotential` 델타, `TopDownAlignmentPotential` 신기록,
`HandSurfaceContactPenalty`, `GraspPosturePenalty`, `ThumbDownPenalty`, `LiftTiltPenalty`,
`ArmActionRatePenalty`, `NearObjectActionPenalty`, `ClosureFarPenalty`, `ClosurePotential`
신기록, `ClosedHandAscentPenalty` — **12항**. 여기에 물리 틱에서 `ContactPotential`·
`GraspConfirmReward`·`LiftPotential`, 종료 시 `LiftSuccessReward`/`FailurePenalty` 6종.

이 구조가 실제로 손해를 냈던 이력이 코드·YAML 주석에 그대로 남아 있다:

- **엄지 각도 페널티** — 에피소드당 -20.0 vs 획득 가능한 총 보상 +12.2. 정책이 "움직이지
  않는 것"으로 수렴해 `ContactCount`가 2M 스텝 동안 0. 두 번(가중치 완화 → 측정 기반
  재정의) 고쳐서야 잡혔다.
- **기울기 무비용** — §1-6.
- **스폰 방위 균일분포** — 600k 스텝을 학습 신호 없이 태웠다(`SpawnAzimuthRadians` 주석).

**항이 하나 늘 때마다 다른 모든 항과의 상대 크기를 사람이 재계산해야 하는 구조**다. 여기에
비전 노이즈·다중 물체·파지점 선택을 얹으면 튜닝 비용이 조합적으로 는다. 재설계에서 줄여야
할 1순위.

### 1-8. 도메인 랜덤화가 사실상 없다

환경 파라미터로 흔드는 값: `cube_width`, `cube_height`, `cube_com_height_fraction`,
`topple_limit_deg` + 보상 스케일 5종. 즉 **물체 치수와 COM만** 흔든다.

없는 것: 마찰계수, 질량(치수에서 결정적으로 계산됨 — `CurrentCubeMass`), 드라이브 게인,
센서 노이즈, 지연, 카메라 외부 파라미터 오차, 초기 자세, 조명. 로드맵이 기록한 대로 COM
하나만 바꿔도 99.7% → 96.6%(`eval_com050`)로 떨어진다 — 일반화 여유가 얇다.

### 1-9. 부차 지적 (재설계의 선행 조건이 되는 것들)

- 드라이브 게인 `ArmDriveStiffness = 10000` / `ArmDriveDamping = 200`이 **미검증**이라고
  코드가 스스로 주석에 적고 있다(2026-09-04). 정책을 재설계하기 전에 물리 충실도를 확정하지
  않으면, 재학습 결과가 나중에 게인 재튜닝으로 다시 무효화된다.
- `TrainingSpeedFraction = 0.5`도 측정값이 아니라 의도적 여유치라고 주석에 명시돼 있다.
- 중력 OFF 유지 근거가 로드맵 §6에 있는데, **중력 없이 "안정적 파지"는 정의되지 않는다.**
  R4를 다루려면 이 전제부터 재검토해야 한다.

## 2. 재설계 원칙 — 무엇을 지키고 무엇을 바꾸나

### 지킬 것

1. **상태 기반 관찰을 유지한다. end-to-end 비주얼 RL로 가지 않는다.**
   로드맵 §2가 이미 내린 결론이고 근거가 유효하다 — RTX 4070 Ti 1대 / 1인 체제에서 픽셀
   입력 PPO는 샘플 수요가 크게 늘고, sim2real 갭이 물리에서 **렌더링으로** 옮겨간다(그러면
   도메인 랜덤화 부담이 조명·재질·노출까지 확장된다). 비주얼 서보잉은 상태 기반 파이프라인이
   실물에서 도는 것을 확인한 **뒤에** 얹을 선택지로 남긴다.
2. **PPO / ML-Agents / Unity PhysX 스택 유지.** 알고리즘 교체는 이 변경의 대상이 아니다.
3. **팔 액션 = 관절 델타 유지.** 실물 경로가 RTDE `servoJ`라 관절 공간이 그대로 나가고,
   IK를 새 실패 지점으로 들이지 않는다(작업공간 IK는 로드맵 v9.1에서 이미 한 번 걷어낸
   이력이 있다).
4. **접촉 플래그의 역할.** 파지 순간 손목 카메라가 가려지는 구간을 촉각이 받는 구성은 이미
   옳다(로드맵 §2). 재설계에서 오히려 강화한다.
5. **1인 체제 운영 도구와 습관** — `picknplace_monitor.py --gate`, `archive_run.py`,
   "왜 이 값인지를 주석에 남기기".

### 바꿀 것 (요약)

| 축 | 현행 | 변경안 |
|---|---|---|
| 물체 정보 출처 | 시뮬레이터 ground truth 직접 읽기 | **가상 추정기 계층**을 거친 값만 (노이즈·지연·드롭아웃·가림) |
| 물체 표현 | 위치·속도·각속도 (자세 없음) | **클래스 + 6D 자세 + 신뢰도·유효 플래그·경과시간** |
| 파지점 | 상수 오프셋 1개 | **물체별 주석된 파지 후보 N개 + 정책이 선택** |
| 물체 종류 | 큐브 1종 | **최소 3종 + 방해물**, 치수·질량·마찰·초기 자세 랜덤화 |
| 손 액션 | 스칼라 1개(20관절 일괄 보간) | **3그룹**(엄지 / 검지·중지 / 약지·소지) |
| 접근 자세 | top-down 강제 | 파지 후보의 접근축 기준 정렬 (top-down은 그 특수해) |
| 성공 판정 | 10 cm 상승 0.5초 유지 | **외란 시험 통과** |
| 보상 | per-decision 12항 수동 튜닝 | **4블록**으로 축약, 자세 요구는 종료 판정/하드 제약으로 이관 |
| 랜덤화 | 치수·COM | 물리 + 센서 + 장착변환 + 지연 |

## 3. 아키텍처 — 인식과 제어를 분리한다

```text
[손목 카메라] ─▶ 인식 모듈 (RL 아님)                  ─▶ [RL 정책]    ─▶ UR16e + DG-5F
                 · 물체 검출/분류                          관찰 v2         (RTDE servoJ /
                 · 6D 자세 추정                            액션 v2          dgsdk)
                 · 파지 후보 생성(물체 모델 주석 기반)
                 · 신뢰도 / 유효 플래그
                        ▲
                        └── 시뮬에서는 "가상 추정기"가 이 인터페이스를 흉내낸다
                            (ground truth + 노이즈 + 지연 + 가림 + 드롭아웃)
```

**핵심은 인터페이스를 먼저 고정하는 것이다.** 시뮬의 가상 추정기와 실물의 진짜 추정기가
**같은 구조체**를 내놓으면, 정책은 값이 어느 쪽에서 왔는지 구분할 수 없다. 이것이 R1을
만족시키는 가장 저렴한 방법이다 — 렌더링을 실사에 맞추는 대신 **추정기 출력의 분포**를
맞춘다.

### 3-1. 인식 인터페이스 (제안 명세)

한 프레임의 출력 = `PerceivedObject` 리스트. 정책에 넘어가는 것은 그중 **타깃 1개 +
방해물 요약**이다.

| 필드 | 형태 | 실물 조달 | 시뮬 조달 |
|---|---|---|---|
| `classId` | one-hot K | 검출기 분류 결과 | 스폰한 프리팹 종류 + 오분류 확률 |
| `poseInBase` | 위치3 + 회전6 | 카메라 자세 추정 × 손목 FK | GT + 노이즈 |
| `poseInPalm` | 위치3 + 회전6 | 추정기 raw + 장착변환 | GT + 노이즈 |
| `confidence` | float | 검출기 점수 | 가림률·거리에서 합성 |
| `isVisible` | bool | 이번 프레임 검출 성공 여부 | 손·팔에 의한 가림 판정 |
| `ageSeconds` | float | 마지막 갱신 후 경과 | 동일 |
| `graspCandidates[N]` | 자세(위치3+회전6) + 점수 + 필요 개구폭 | 물체 모델 주석 조회 | 동일(프리팹 주석) |

회전은 **쿼터니언(4)이 아니라 6D 연속표현(회전행렬의 앞 두 열)** 으로 넣는다. 쿼터니언의
이중피복(q ≡ −q)이 신경망 입력에서 불연속을 만들고, 관찰 정규화를 끄고 쓰는 이 설정
(`normalize: false`)에서는 더 나쁘다.

> **`isVisible` / `ageSeconds`를 반드시 넣는 이유.** 로드맵 §2가 지적한 대로 **파지 순간
> 손목 카메라는 손가락과 물체에 가려진다.** 가려진 구간을 "마지막으로 본 값을 계속
> 흘려보내기"로 때우면 정책은 그게 낡은 값인지 알 수 없다. 유효 플래그와 경과시간을 주면
> 정책이 "지금은 촉각과 고유수용감각으로 간다"를 **학습할 수 있다.** 이 두 칸이 없으면
> 그 인계는 원리적으로 학습 불가능하다.

### 3-2. 파지 후보는 어디서 오나

**물체 프리팹에 주석으로 박는다.** 새 컴포넌트 `GraspAffordance`(제안,
`unity/Assets/MLAgents/picknplace/Runtime/`)가 물체 로컬 좌표계에 파지 자세 목록(자세 +
필요 개구폭 + 점수)을 들고 있고, 씬 빌더가 스폰할 때 함께 실린다.

| 물체 | 후보 |
|---|---|
| 큐브(현행) | 4측면 + 상단 = 다수. **현행 top-down 해가 그중 하나로 자연 포함 → 기존 정책과의 비교 가능성 유지** |
| 원통 | 측면 원주 방향 다수 + 상단 1개 |
| FOUP 프록시 | **손잡이 1개**(정답에 가까움) + 림 2개(가능) + 그 외(불가) |

정책은 "후보 중 하나를 고르는 것"을 **명시적 이산 액션으로 갖지 않는다.** 대신 관찰에
후보들이 들어가고, 보상은 **어느 후보로 갔든 실제로 성공하면** 지급된다. 즉 선택은 연속
제어 안에 암묵적으로 담긴다. 이산 선택 헤드를 두지 않는 이유는 하이브리드 액션 공간이 PPO
튜닝을 어렵게 만들고, 후보 개수가 물체마다 달라 액션 shape이 가변이 되기 때문이다.

## 6. 보상 v2 — 12항을 4블록으로

### 설계 규칙 (이 프로젝트의 실패에서 역산한 것)

1. **자세 요구를 per-decision 비용으로 표현하지 않는다.** 엄지 페널티 사건(§1-7)의 교훈:
   200결정 × 작은 비용이 태스크 보상 총량을 삼킨다. 자세 요구는 **① 성공 판정에 넣거나
   ② 액션/관절 범위 하드 제약으로** 표현한다.
2. **새 항을 넣을 때 "에피소드 전체를 최악으로 보내도 성공 1회 보상보다 싸다"를 산술로
   확인하고 그 계산을 주석에 남긴다.** 현행 `LiftTiltPenaltyScale` 주석이 이미 이 규율을
   지키고 있다 — 관례로 승격시킨다.
3. **셰이핑은 포텐셜 차분으로만.** 현행이 이미 지키는 규율. 유지.
4. **한 관심사에 한 항.** top-down 정렬이 `TopDownAlignmentPotential`(보상)과
   `GraspPosturePenalty`(벌점)로 두 번 표현된 것 같은 중복을 만들지 않는다.

### 블록 구성

| 블록 | 항 | 형태 | 비고 |
|---|---|---|---|
| **S. 성공** | 안정 파지 성공 | 희소 대형(+5 급) | §7 외란 시험 통과 시 |
| | 파지 확정 | 신기록 포텐셜(+1 급) | 현행 `GraspConfirmReward` 유지 |
| **A. 접근 셰이핑** | 최근접 파지 후보까지 거리 | 포텐셜 차분 | **물체 중심이 아니라 후보 파지 자세까지의 거리** |
| | 후보 접근축 정렬 | 신기록 포텐셜 | top-down 상수 대신 **후보가 지정한 접근 방향** |
| | 접촉 개수 | 신기록 포텐셜 | 현행 `ContactPotential` 유지 |
| **F. 실패** | 낙하 / 밀어냄 / 범위이탈 / 전도 | 종료 + 벌점 | 현행 유지 |

| **C. 비용** | 시간 | 상수 소액 | 현행 유지 |

| | 손-바닥 긁힘 | 시간 비례 | 현행 유지(실물 손상 요인) |

### 삭제·이관되는 현행 항

| 현행 항 | 처리 | 이유 |
|---|---|---|
| `ThumbDownPenalty` | **삭제 → 성공 판정으로 이관** | 두 번 고쳐도 계속 문제였다. "엄지가 바닥을 향하지 않는다"는 요구는 파지 후보의 접근축을 따르면 자동 만족되거나, 외란 시험을 못 견뎌 실패로 드러난다 |
| `GraspPosturePenalty` | **삭제** | 기본 스케일이 이미 `0f`(비활성). 후보 접근축 정렬(A블록)이 대체 |
| `TopDownAlignmentPotential` | **일반화** | "베이스 −up 방향"이 아니라 "후보 접근축" 기준으로. 큐브 상단 후보에서는 현행과 동일하게 동작 |
| `ClosedHandAscentPenalty` | **삭제 검토** | 빈손으로 손 닫고 올라가는 행동을 막는 항인데, 외란 시험 기반 성공 판정에서는 애초에 보상이 없어 유인이 사라진다 |
| `LiftTiltPenalty` | **성공 판정으로 이관** | 외란 시험이 기울어진 파지를 자동으로 걸러낸다. 별도 per-decision 비용 불필요 |

**결과: per-decision 항 12개 → 7개**(그중 셰이핑 3, 비용 4). 사람이 상대 크기를 맞춰야 하는
항이 절반 가까이 준다.

## 7. 성공 판정 v2 — 외란 시험 (R4의 핵심)

현행 "10 cm 상승 + 0.5초 유지"를 다음으로 대체한다.

```text
파지 확정  (기존 force-closure 유사 기하 판정 유지)
      │
      ▼
1) 리프트     : 물체를 CurrentLiftTargetHeight까지 상승 (기존 커리큘럼 유지)
      │
      ▼
2) 외란 시험  : DisturbanceSeconds 동안 스크립트된 외란 인가
                · 손목에 랜덤 방향 정현파 가속 (진폭·주파수는 환경 파라미터)
                · 또는 물체에 랜덤 렌치 임펄스 N회
      │
      ▼
3) 성공 조건  : 시험 종료 시점에 아래를 모두 만족
                · 접촉 유지 (파지 기하 판정이 계속 성립)
                · 손 기준 좌표계에서 물체 이동량 ≤ SlipToleranceMeters
                · 물체 기울기 변화 ≤ TiltToleranceDegrees
```

- **이 시험 하나가 §1-6의 구멍과, `LiftTiltPenalty`·`ThumbDownPenalty`가 대리하려던 문제를
  함께 닫는다.** 기울여 잡은 파지, 손끝 하나에 걸친 파지, 엄지가 어정쩡한 파지는 외란에서
  미끄러진다 — 사람이 그걸 페널티 계수로 표현할 필요가 없어진다.
- 외란 강도는 **환경 파라미터**로 두고 커리큘럼으로 올린다(§8). 강도 0에서 시작하면 현행
  태스크와 동일해지므로 기존 체크포인트가 그대로 출발점이 된다.
- **선행 조건: 중력 ON.** 현행 중력 OFF 유지 근거(로드맵 §6)는 안정 파지를 다루는 순간
  무효다. 중력을 켜면 드라이브가 실제로 하중을 버텨야 하므로 §1-9의 게인 검증이 **선행
  조건**이 된다. 이 순서를 뒤집으면 안 된다.

### 새 지표 (`RecordOutcome`에 추가 제안)

| 태그 | 의미 |
|---|---|
| `PicknPlace/DisturbanceSurvived` | 외란 시험 통과율 (새 성공률) |
| `PicknPlace/SlipDuringDisturbanceMeters` | 시험 중 손 기준 물체 이동량 |
| `PicknPlace/PoseErrorAtGraspMeters` | 파지 순간 인식 추정 오차 (GT 대비) |
| `PicknPlace/OcclusionFraction` | 에피소드 중 `isVisible == false` 비율 |
| `PicknPlace/SelectedCandidateIndex` | 어느 파지 후보로 수렴했는지 (분포로 관찰) |
| `PicknPlace/WrongObjectGrasp` | 방해물 오파지율 |

`training/scripts/picknplace_monitor.py`의 표시 항목과 `--gate` 기준도 함께 갱신 대상이다 —
현행 게이트는 `PicknPlace/Success`·`ContactCount`·`GraspConfirmed`·`MaxPalmFacingAlignment`를
본다. **`Success`의 정의가 바뀌므로 과거 런과 곡선을 직접 비교하면 안 된다**(현행 코드가
`LiftTiltPenalty` 도입 때 성공 정의를 일부러 건드리지 않은 것과 같은 이유 — 이번에는 정의를
바꾸는 쪽이므로, 새 런은 새 기준선으로 취급한다).

## 8. 커리큘럼 v2

현행 `grasp_stage` 1~3(스폰 반경 + 리프트 목표/유지시간)은 **단계 0의 내부 구조로 흡수**하고,
그 위에 축을 하나 더 얹는다. 축을 분리하는 이유: 운동 기술과 인식 강건성을 동시에 올리면
어느 쪽이 막혔는지 분리 진단이 안 된다.

| 단계 | 인식 | 물체 | 외란 | 목적 | 초기값 |
|---|---|---|---|---|---|
| **0** | 오라클(노이즈 0) | 큐브 1종 | 없음 | 현행 태스크 재현 — **파이프라인 정합성 확인** | 기존 체크포인트 슬롯 확장 |
| **1** | 노이즈 + 지연 램프업 | 큐브 1종 | 없음 | 추정 오차 하에서 운동 기술 유지 | 0단계 |
| **2** | + 가림 / 드롭아웃 | 큐브 1종 | 없음 | 촉각 인계 학습(`isVisible` 활용) | 1단계 |
| **3** | 동일 | **3종 + 방해물** | 없음 | 식별·파지점 선택 (R2·R3) | 2단계 |
| **4** | 동일 | 3종 + 방해물 | **램프업** | 안정 파지 (R4) | 3단계 |

- 승급 기준은 현행처럼 `completion_criteria: progress` + `min_lesson_length`로 둔다. 단
  **단계 3 이후는 `PicknPlace/DisturbanceSurvived` 기준으로 판정**해야 의미가 있다.
- **단계 0이 이 계획의 안전장치다.** 관찰·액션·씬을 전부 바꾼 뒤 "학습이 안 되는데 재설계
  탓인지 구현 버그 탓인지 모르는" 상황을 막는다. 단계 0에서 현행과 비슷한 성공률이 안 나오면
  그건 설계 실패가 아니라 버그다.
- 학습 설정은 **기존 `dg5f_picknplace.yaml`을 보존하고 새 파일**(`dg5f_picknplace_v2.yaml`
  등)로 낸다 — 과거 런과의 비교 가능성을 남기기 위해. 현행 파일명 규약(파일 이름이 곧 실험
  이름)을 그대로 따른다.

## 11. 선행 조건 — 이거 없이 착수하면 재작업이 난다

| # | 선행 조건 | 현재 상태 | 막히면 생기는 일 |
|---|---|---|---|
| **P1** | **웨이퍼 케이스(FOUP) 사양** — 치수·질량·파지 지점·허용 기울기 | 미확보(로드맵 §4 스펙 요구 목록) | 물체 3종 중 가장 중요한 하나를 추정으로 만들게 됨 → §8 단계 3 재작업 |
| **P2** | **드라이브 게인 검증**(`ArmDriveStiffness`/`Damping`) | **미검증**(코드 주석이 자인) | 중력 ON + 외란 시험이 게인 탓에 실패하는데 정책 탓으로 오진 |
| **P3** | **중력 ON 전환 결정** | 현행 OFF | R4(안정 파지)가 정의되지 않음 |
| **P4** | **손목 카메라 장착 위치·변환** | Orbbec Gemini 305 구매 승인 대기, 임시 웹캠 | 가상 추정기의 가림 모델과 장착변환 오차 분포를 정할 수 없음 |
| **P5** | **dgsdk 접촉력 값 확인** — `get_fingertip_sensor_data()`가 이진인지 아날로그인지 | 미확인 | 관찰 B블록 접촉력 6칸의 존폐 |
| **P6** | `TrainingSpeedFraction` 실측 | 여유치 0.5 (측정값 아님) | 실물 속도 envelope 불일치 |

**P1·P4가 없어도 §8 단계 0~2는 착수 가능하다** — 큐브 1종 + 가상 추정기만 있으면 되고,
그 구간이 이 재설계에서 가장 위험한 부분(관찰 구조 교체)이다. **P2·P3는 단계 4 이전에 반드시
해소.** 이 순서로 가면 스펙 대기와 개발이 병렬로 돈다.

## 12. 채택하지 않은 대안과 이유

| 대안 | 왜 안 하나 |
|---|---|
| **end-to-end 비주얼 RL**(픽셀 → 액션) | 샘플 수요와 렌더링 sim2real 갭. 로드맵 §2 결론 유지. 상태 기반이 실물에서 돈 뒤 비주얼 서보잉으로 얹는 것이 순서 |
| **작업공간(Cartesian) 액션 + IK** | 로드맵 v9.1에서 걷어낸 경로를 되살리는 것. RTDE `servoJ`와 직결되는 관절 액션이 실물 경로와 일치한다 |
| **손가락 20관절 개별 액션** | 탐색 공간 폭증 대비 이득 불확실. 검증된 `RightFistDeg`를 그룹 적용하는 쪽이 기존 실측 자산을 살린다 |
| **파지 후보 이산 선택 헤드** | 하이브리드 액션 공간이 PPO 튜닝을 어렵게 하고, 후보 수가 물체마다 달라 액션 shape이 가변이 된다 |
| **현행 보상에 항만 추가** | §1-7 이력이 반증. 항이 늘수록 상대 크기 재계산 비용이 조합적으로 증가한다 |
| **알고리즘 교체(SAC 등)** | 지금 병목은 알고리즘이 아니라 **관찰이 실물에 없는 정보를 쓰고 있다는 것**. 축을 하나만 움직인다 |
| **기존 체크포인트 폐기 후 완전 재학습** | 로드맵이 "기존 자산은 재학습 초기값으로 쓴다"고 정해둠. §8 단계 0의 슬롯 확장 부트스트랩으로 살릴 수 있다 |

## 13. 요약 — 한 장

- 현행 정책은 **시뮬레이터가 물체 위치·속도를 직접 알려주는 전제** 위에 서 있다. 손목
  카메라를 물리적으로 붙여도 이 전제가 남아 있으면 카메라는 학습에서 아무 역할도 하지 않는다.
- 그래서 1순위로 바꿀 것은 카메라 추가가 아니라 **관찰의 출처를 추정기 인터페이스로 강제하는
  것**이다. 시뮬은 그 인터페이스를 노이즈·지연·가림으로 흉내낸다.
- **파지점을 상수 오프셋에서 물체 주석 후보로 바꾸면** "알아서 파지점을 식별"이 비로소 학습
  가능한 문제가 된다. 손 액션을 3그룹으로 늘려야 그 선택이 손 모양에 반영된다.
- **"안정적 파지"는 외란 시험으로 정의한다.** 그러면 지금까지 사람이 페널티 계수로 대리하던
  자세 요구(엄지·기울기)를 보상에서 걷어낼 수 있고, per-decision 항이 12개에서 7개로 준다.
- **단계 0(오라클 유지)을 반드시 거친다.** 재설계 실패와 구현 버그를 구분하는 유일한 방법.
