## 세션 1 — 종이컵 옆 파지 시연 중 발견: D-2 채점표가 "관절에 낀 상태"도 성공으로 센다

### 경위

사용자에게 파지 강화학습 결과를 직접 보여 주려고 `superdex/scripts/watch_grasp.py`로
종이컵(`paper_cup`)을 옆에서 잡는 자세(D-2 채점표의 `tilt+45`/`tilt+90` 행,
둘 다 채점표상 성공률 100%)를 시연했다. 사용자가 화면으로 보고 지적:
"손가락으로 파지를 하는게 아니라 종이컵이 엄지손가락의 1번 관절에 끼어있는걸
나머지 손가락으로 겨우 잡는 식"이고 "바들바들 떨고있다".

### 코드로 1차 확인 — 채점 기준이 손끝(지문) 5곳만 본다

`superdex/envs/dg5f_grasp_env.py` 833행 `n_tips = int(np.sum(tip_force > ...))`가
성공 판정(`is_success`)과 학습 보상 모두의 근거인데, `tip_force`는 **손끝
(`TIP_LINKS`, 5곳) 각각에 대해서만** 접촉력을 잰다(503~516행 — 손끝 링크만 따로
actor 핸들을 만든다). 엄지 뿌리 관절 등 손끝이 아닌 부위는 **힘을 잴 방법 자체가
코드에 없다.** 그래서 물체가 손끝이 아닌 부위에 끼어서 버텨도, 손끝 3곳(min_tips)만
살짝 닿아 있으면 "파지 성립 100%"로 채점표(D-2, `pose_score_18obj.json` 등)에
기록된다.

### 실측으로 2차 확인 — 관절에 실리는 힘이 물리적으로 말이 안 되는 크기다

새 진단 스크립트 `superdex/scripts/diagnose_wedge_contact.py`를 만들어(같은
`block.get_contact_force_from_actor_world()` API를 손끝이 아닌 모든 손가락 관절
링크에도 적용), `--object paper_cup --place 0.05,0.0,0.03 --place-rot
0.3826834323650898,0.0,0.0,0.9238795325112867`(tilt+45, 채점표상 성공률 100%)로
10 에피소드를 돌렸다:

- **10개 에피소드 전부**에서 손끝이 아닌 관절에 유의미한 힘이 실렸다.
- 크기가 물리적으로 말이 안 된다 — 종이컵(가벼운 물체, 버티는 데 1 N 안팎이면
  충분) 인데 **에피소드 중 최댓값이 수백~11,340 N**, 그리고 일시적 충돌이 아니라
  **마지막 스텝(다 잡고 유지 중인 상태)에서도 수백~3,435 N이 계속 유지**된다
  (예: 시드 9001 마지막 스텝 `dg5f_link_5_2=757N, dg5f_link_5_3=729N`, 시드 9005
  마지막 스텝 `dg5f_link_4_2=3435N, dg5f_link_4_3=2607N`).
- 손끝(지문) 힘은 같은 시점에 대체로 한 자릿수~수십 N으로 훨씬 그럴듯한 크기다.
- 이번 측정에서는 손가락 4·5번(링크 이름 `dg5f_link_4_*`, `dg5f_link_5_*`) 쪽이
  가장 심했다 — 사용자가 눈으로 지목한 "엄지(1번)"와 정확히 같은 손가락은 아닐 수
  있지만(URDF상 손가락 번호와 눈으로 보는 "엄지" 인식이 다를 수 있음), **메커니즘은
  동일**: 손끝이 아닌 부위가 비정상적으로 큰 힘으로 물체를 지탱하고 있다.

### 판정 (잠정)

수백~수천 N이 종이컵 하나를 놓고 계속 유지된다는 건 "살짝 걸쳐서 버티는 편법"
정도가 아니라 **물체 메시가 손가락 관절 속으로 깊이 파고들어 있고, 접촉 솔버가
그걸 매 스텝 밀어내려 하는 상태(관통/불안정)일 가능성이 높다** — 이게 화면에서
"바들바들 떨림"으로 보였을 것이다. 다만 이건 이번 실측 스크립트로 확인한 **1차
가설**이고, 아래 "다음에 할 일"의 검증이 더 필요하다.

⚠️ 원래 게이트 0·2·4 판정(§0 "증거 3·4", 파지 성립률 100%)은 **기본 배치
(duck_lamp, 위에서 접근, 사람이 맞춘 place 상수)** 로 검증된 것이라 이 문제와는
별개일 수 있다 — 이번에 문제가 드러난 조합은 **종이컵 + D-2 스윕이 만들어낸
옆/기울인 자세**다. 즉 "SuperDex 채택 자체가 잘못됐다"가 아니라 "D-2 채점표의
성공률을 곧이곧대로 못 믿는다"에 가깝다.

### 영향

- **D-2 채점표**(`superdex/results/pose_score_*.json`) 의 `rate`(성공률)를
  "잘 잡았다"의 증거로 쓸 수 없다 — 흔들림·관통을 전혀 안 본다.
- **D-4**(자세 예측기 학습)가 이 채점표를 정답으로 학습 중이었다 — 관절에 낀 자세를
  "좋은 자세"로 잘못 가르치고 있었을 가능성. D-4가 기하학 어림값을 못 이기는 것과
  이게 관련 있는지는 미확인.

### 결론

**코드는 준비됐다.** 이 리눅스 노트북에서 리눅스용 그리퍼 코드(`dg5f_sdk_bridge_dgsdk.py`)가
- 실제 리눅스 라이브러리 파일을 열 수 있고(제조사 버전 번호까지 정상적으로 읽힘),
- 드라이런으로 정상 시작하고,
- 웹캠 프로그램이 보내는 것과 같은 모양의 신호를 받아 처리하는 것까지 확인됨.

**아직 못 확인한 것** — 이건 실물(그리퍼 전원+랜선 연결) 없이는 원천적으로 확인 불가:
1. `connect_to_gripper()` 호출 시 충돌(access violation)이 나는지 — 문서에 적힌 미해결 위험 ①
2. 연결 직후 PID 게인을 안 넣으면 전 관절이 무반응이라는 예전 실측이 이 경로에서도 똑같이
   나는지 — 위험 ②

### 그리퍼 IP 확정 — `.env`에 채워 넣음

사용자 확인: 그리퍼를 받은 시점 이후로 IP를 바꾼 적이 없고, 매뉴얼에 적힌 값은
`169.254.186.72:502`(링크로컬 대역 — 예상과 일치). `.env`의 `RTAUTO_DG5F_IP`에 채워

## 세션 5 — 팔·손목 관절 물리 스프링(떨림) 제거

### 사용자 보고 + 요청

### 원인 (코드 확인)

UR16e 6축(팔+손목) 관절은 유니티 물리엔진의 `ArticulationBody` 스프링 드라이브
(`xDrive` — stiffness 10000·damping 200·forceLimit 100000, 값 출처
`tools/urdf_hand_import/setup_drive.py`)로 목표각을 쫓아간다. 목표각이 천천히 바뀔 땐
안 보이다가 빠르게 바뀌면 스프링이 목표를 지나쳤다 되돌아오며 떤다.

이 스프링을 쓰는 경로가 두 개였다:
1. URSim/실물 → 화면 반영 (`UrArmTwinDriver.cs`) — 세션 이전(대화 앞부분)에 먼저 고침.
2. 화면 안에서 슬라이더/IK로 직접 조작 → URSim (`HandSliderUI.cs`, `ArmTargetIK.cs`가
   `HandSliderUI.armJoints[i].value`에 써서 간접 구동) — **이번에 고침**.

### 한 일 (코드 변경, Unity 에디터로 컴파일 확인은 못 함 — 아래 "확인 못 한 것" 참고)

|---|---|
| `unity/Assets/Scripts/UrArmTwinDriver.cs` | `bypassPhysicsSpring`(기본 true) 추가 — 목표각을 매 물리 틱마다 `jointPosition`/`jointVelocity`에 직접 적용, 스프링 힘을 거치지 않음. 기존 lerp·최대각속도 clamp는 그대로 유지(부드러움은 보존) |
| `unity/Assets/Scripts/HandSliderUI.cs` | `Apply()`에 `bypassSpring` 매개변수 추가. **팔(`armJoints`)만** true로 호출 — 손가락(`handJoints`)은 자가충돌 버티려 스프링이 필요하다는 기존 설계 근거(`RobotConfig.cs` 주석)가 있어 그대로 스프링 유지 |

환경 쪽 팔 관절 드라이브(`RobotConfig.cs`, ML-Agents 에이전트들)는 건드리지 않음 —
거기는 물리적으로 그럴듯한 토크 제한 동역학이 의도된 설계일 수 있어 이번 요청 범위 밖으로
판단.

- **순서대로 거치는 구조가 아니다.** URSim은 실물의 대역이고, 실물이 연결되면
  중계 프로그램(`arm/ur_rtde_bridge.py`)이 말을 거는 주소만 `127.0.0.1`(URSim)에서
  실물 컨트롤박스 IP로 바뀐다 — 소프트웨어·구조는 동일(`docs/SIM2REAL_ROADMAP.md` §9
  "접속 대상만 교체"가 정본 근거).
- **티칭 펜던트는 실시간 명령이 지나가는 통로가 아니라 안전 스위치.** 전원 ON·브레이크
  해제·Local↔Remote Control 전환용. Remote Control로 바꾼 뒤에는 움직임 명령이
  펜던트를 거치지 않고 PC→컨트롤박스로 직접 간다. URSim이든 실물이든 이 수동 절차는
  매번 똑같이 필요하다.

## 세션 8 — 실물 연결 전 하드코딩 IP 전수 재점검

사용자 요청: "실물 연결 전에 코드에서 하드코딩된 IP 처리 다시 확인해줘."

### 확인한 것 (직접 grep, 전 리포)

| 범위 | 방법 | 결과 |
|---|---|---|
| 전 파이썬 파일의 IP 리터럴(`127.0.0.1`/`192.168.*`/`169.254.*`/`10.*`) | grep | `config/rtauto_config.py`의 정당한 기본값과 사용법 주석뿐 — 로직에 박힌 값 없음 |
| `config/rtauto_config.py`를 안 거치고 `os.environ.get("RTAUTO...")`을 직접 쓰는 다른 파일이 있는지 | grep | `vision/dg5f/dg5f_teleop_gui.py` 하나뿐 — exe 배포 목적으로 이미 코드 주석에 이유가 적힌 의도된 예외 |
| 유니티 C# 스크립트의 IP 문자열 리터럴 | grep | `UrArmSender.cs`/`Dg5fSender.cs`의 `bridgeIp = "127.0.0.1"`은 `RtautoConfig.GetString(키, bridgeIp)`의 **최후 기본값**으로만 쓰여 정상. `Dg5fTwinModeSwitcher.cs`도 `RtautoConfig.GetString` 경유로 정상 |
| 셸/파워셸 스크립트 | grep | 하드코딩 없음 |

### 발견·수정한 버그

`vision/dg5f/dg5f_teleop_gui.py`의 "실물 SDK 브리지" 기본 주소(`DEF_REAL_IP`)가 **`RTAUTO_UNITY_IP`를 잘못 재사용**하고 있었다 — Unity가 도는 곳과 그리퍼 브리지(`dg5f_sdk_bridge.py`)가
도는 곳이 다른 컴퓨터면 조용히 어긋난다. **9월 21일 세션에서 고친 `UrArmSender.cs`의
IP 분리 버그와 같은 유형.** 이미 존재하던 전용 키 `RTAUTO_DG5F_BRIDGE_IP`로 교체.

```python
# 고치기 전
DEF_REAL_IP = os.environ.get("RTAUTO_UNITY_IP", "127.0.0.1")   # 실물 SDK 브리지
# 고친 뒤
DEF_REAL_IP = os.environ.get("RTAUTO_DG5F_BRIDGE_IP", "127.0.0.1")   # 실물 SDK 브리지
```

`python -m py_compile vision/dg5f/dg5f_teleop_gui.py`로 구문 오류 없음 직접 확인함.

   빌드에도 반영되는지 다음에 빌드할 때 확인 필요(이번엔 소스만 고침, 빌드 안 함).
3. 실물 연결 시 `.env`의 `RTAUTO_DG5F_BRIDGE_IP`가 "그리퍼 브리지 프로그램이 도는 PC"
   주소로 올바르게 채워져 있는지 확인(그리퍼 자신의 IP인 `RTAUTO_DG5F_IP`와 다른 값 —
   이 문서 세션 2~3에서 이미 헷갈리기 쉽다고 문서화한 것과 같은 함정).
