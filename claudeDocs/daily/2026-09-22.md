## 세션 1 — 종이컵 옆 파지 시연 중 발견: D-2 채점표가 "관절에 낀 상태"도 성공으로 센다

### 경위

사용자에게 파지 강화학습 결과를 직접 보여 주려고 `superdex/scripts/watch_grasp.py`로
종이컵(`paper_cup`)을 옆에서 잡는 자세(D-2 채점표의 `tilt+45`/`tilt+90` 행,
둘 다 채점표상 성공률 100%)를 시연했다. 사용자가 화면으로 보고 지적:
"손가락으로 파지를 하는게 아니라 종이컵이 엄지손가락의 1번 관절에 끼어있는걸
나머지 손가락으로 겨우 잡는 식"이고 "바들바들 떨고있다".

### 코드로 1차 확인 — 채점 기준이 손끝(지문) 5곳만 본다

`superdex/envs/dg5f_grasp_env.py` 833행 `n_tips = int(np.sum(tip_force > ...))`가
성공 판정(`is_success`)과 학습 보상 모두의 근거인데, `tip_force`는 **손끝
(`TIP_LINKS`, 5곳) 각각에 대해서만** 접촉력을 잰다(503~516행 — 손끝 링크만 따로
actor 핸들을 만든다). 엄지 뿌리 관절 등 손끝이 아닌 부위는 **힘을 잴 방법 자체가
코드에 없다.** 그래서 물체가 손끝이 아닌 부위에 끼어서 버텨도, 손끝 3곳(min_tips)만
살짝 닿아 있으면 "파지 성립 100%"로 채점표(D-2, `pose_score_18obj.json` 등)에
기록된다.

### 실측으로 2차 확인 — 관절에 실리는 힘이 물리적으로 말이 안 되는 크기다

새 진단 스크립트 `superdex/scripts/diagnose_wedge_contact.py`를 만들어(같은
`block.get_contact_force_from_actor_world()` API를 손끝이 아닌 모든 손가락 관절
링크에도 적용), `--object paper_cup --place 0.05,0.0,0.03 --place-rot
0.3826834323650898,0.0,0.0,0.9238795325112867`(tilt+45, 채점표상 성공률 100%)로
10 에피소드를 돌렸다:

- **10개 에피소드 전부**에서 손끝이 아닌 관절에 유의미한 힘이 실렸다.
- 크기가 물리적으로 말이 안 된다 — 종이컵(가벼운 물체, 버티는 데 1 N 안팎이면
  충분) 인데 **에피소드 중 최댓값이 수백~11,340 N**, 그리고 일시적 충돌이 아니라
  **마지막 스텝(다 잡고 유지 중인 상태)에서도 수백~3,435 N이 계속 유지**된다
  (예: 시드 9001 마지막 스텝 `dg5f_link_5_2=757N, dg5f_link_5_3=729N`, 시드 9005
  마지막 스텝 `dg5f_link_4_2=3435N, dg5f_link_4_3=2607N`).
- 손끝(지문) 힘은 같은 시점에 대체로 한 자릿수~수십 N으로 훨씬 그럴듯한 크기다.
- 이번 측정에서는 손가락 4·5번(링크 이름 `dg5f_link_4_*`, `dg5f_link_5_*`) 쪽이
  가장 심했다 — 사용자가 눈으로 지목한 "엄지(1번)"와 정확히 같은 손가락은 아닐 수
  있지만(URDF상 손가락 번호와 눈으로 보는 "엄지" 인식이 다를 수 있음), **메커니즘은
  동일**: 손끝이 아닌 부위가 비정상적으로 큰 힘으로 물체를 지탱하고 있다.

### 판정 (잠정)

수백~수천 N이 종이컵 하나를 놓고 계속 유지된다는 건 "살짝 걸쳐서 버티는 편법"
정도가 아니라 **물체 메시가 손가락 관절 속으로 깊이 파고들어 있고, 접촉 솔버가
그걸 매 스텝 밀어내려 하는 상태(관통/불안정)일 가능성이 높다** — 이게 화면에서
"바들바들 떨림"으로 보였을 것이다. 다만 이건 이번 실측 스크립트로 확인한 **1차
가설**이고, 아래 "다음에 할 일"의 검증이 더 필요하다.

⚠️ 원래 게이트 0·2·4 판정(§0 "증거 3·4", 파지 성립률 100%)은 **기본 배치
(duck_lamp, 위에서 접근, 사람이 맞춘 place 상수)** 로 검증된 것이라 이 문제와는
별개일 수 있다 — 이번에 문제가 드러난 조합은 **종이컵 + D-2 스윕이 만들어낸
옆/기울인 자세**다. 즉 "SuperDex 채택 자체가 잘못됐다"가 아니라 "D-2 채점표의
성공률을 곧이곧대로 못 믿는다"에 가깝다.

### 영향

- **D-2 채점표**(`superdex/results/pose_score_*.json`) 의 `rate`(성공률)를
  "잘 잡았다"의 증거로 쓸 수 없다 — 흔들림·관통을 전혀 안 본다.
- **D-4**(자세 예측기 학습)가 이 채점표를 정답으로 학습 중이었다 — 관절에 낀 자세를
  "좋은 자세"로 잘못 가르치고 있었을 가능성. D-4가 기하학 어림값을 못 이기는 것과
  이게 관련 있는지는 미확인.

### 결론

**코드는 준비됐다.** 이 리눅스 노트북에서 리눅스용 그리퍼 코드(`dg5f_sdk_bridge_dgsdk.py`)가
- 실제 리눅스 라이브러리 파일을 열 수 있고(제조사 버전 번호까지 정상적으로 읽힘),
- 드라이런으로 정상 시작하고,
- 웹캠 프로그램이 보내는 것과 같은 모양의 신호를 받아 처리하는 것까지 확인됨.

**아직 못 확인한 것** — 이건 실물(그리퍼 전원+랜선 연결) 없이는 원천적으로 확인 불가:
1. `connect_to_gripper()` 호출 시 충돌(access violation)이 나는지 — 문서에 적힌 미해결 위험 ①
2. 연결 직후 PID 게인을 안 넣으면 전 관절이 무반응이라는 예전 실측이 이 경로에서도 똑같이
   나는지 — 위험 ②

### 그리퍼 IP 확정 — `.env`에 채워 넣음

사용자 확인: 그리퍼를 받은 시점 이후로 IP를 바꾼 적이 없고, 매뉴얼에 적힌 값은
`169.254.186.72:502`(링크로컬 대역 — 예상과 일치). `.env`의 `RTAUTO_DG5F_IP`에 채워

## 세션 5 — 팔·손목 관절 물리 스프링(떨림) 제거

### 사용자 보고 + 요청

### 원인 (코드 확인)

UR16e 6축(팔+손목) 관절은 유니티 물리엔진의 `ArticulationBody` 스프링 드라이브

`tools/urdf_hand_import/setup_drive.py`)로 목표각을 쫓아간다. 목표각이 천천히 바뀔 땐
안 보이다가 빠르게 바뀌면 스프링이 목표를 지나쳤다 되돌아오며 떤다.

이 스프링을 쓰는 경로가 두 개였다:
1. URSim/실물 → 화면 반영 (`UrArmTwinDriver.cs`) — 세션 이전(대화 앞부분)에 먼저 고침.
2. 화면 안에서 슬라이더/IK로 직접 조작 → URSim (`HandSliderUI.cs`, `ArmTargetIK.cs`가
   `HandSliderUI.armJoints[i].value`에 써서 간접 구동) — **이번에 고침**.

### 한 일 (코드 변경, Unity 에디터로 컴파일 확인은 못 함 — 아래 "확인 못 한 것" 참고)

환경 쪽 팔 관절 드라이브(`RobotConfig.cs`, ML-Agents 에이전트들)는 건드리지 않음 —
거기는 물리적으로 그럴듯한 토크 제한 동역학이 의도된 설계일 수 있어 이번 요청 범위 밖으로

  실물 컨트롤박스 IP로 바뀐다 — 소프트웨어·구조는 동일(`docs/SIM2REAL_ROADMAP.md` §9
  "접속 대상만 교체"가 정본 근거).
- **티칭 펜던트는 실시간 명령이 지나가는 통로가 아니라 안전 스위치.** 전원 ON·브레이크
  해제·Local↔Remote Control 전환용. Remote Control로 바꾼 뒤에는 움직임 명령이
  펜던트를 거치지 않고 PC→컨트롤박스로 직접 간다. URSim이든 실물이든 이 수동 절차는
  매번 똑같이 필요하다.

## 세션 9 (이어서) — 실물 D405 + URSim 으로 **경로 전체를 실제로 돌렸다**

앞 기록에서 "장비가 없어 못 돌렸다"고 적었는데, 그 뒤 사용자가 **D405 를 꽂고
URSim 원격 조작(Remote Control)을 켜 줘서** 끝까지 돌렸다. 위 "확인 못 함" 항목은
아래로 갱신된다.

### 실물 D405 가 잡아낸 진짜 버그 — 카메라 기준에서 위아래를 판정하고 있었다

책상에 **똑바로 서 있는** 주스병을 보고 프로그램이 `누워 있음 (기운 각도 81도)` 라고
했다. 원인:

- `posture()` 가 위쪽을 `(0, 0, 1)` 로 **고정**해서 썼다.
- 그런데 카메라 좌표는 **Z 가 앞쪽(거리)** 이다. 세로로 선 병은 카메라 광축과
  직각이라 "누웠다" 로 나온다.
- 카메라가 얼마나 기울어져 있는지는 **팔 자세 + 손목 카메라 장착값**을 알아야 나온다.

**고친 방식**: 카메라 기준 물체에 위아래를 물으면 **조용히 틀린 답을 내는 대신 막는다**
(`ObjectPose._up()` 이 `ObjectPoseError`). 사람이 보는 한 줄만 예외를 삼켜
"아직 모름 — 카메라 기준이라 어느 쪽이 위인지 알 수 없다" 로 적는다.
시험 3개 추가(`TestPostureNeedsBaseFrame`).

⚠️ 이건 **숫자만 봤으면 못 찾았을 버그다** — 사진과 대조해서 찾았다(원칙 6).

### `--plan` 이 관절각을 안 풀어 보던 구멍

`--plan` 이 팔에 붙어 좌표까지만 내고 **관절 각도가 풀리는지는 확인하지 않았다**
(`ArmMover.plan()` 을 안 불렀다). "갈 수 있는지" 를 확인하는 것이 `--plan` 의 존재
이유인데 그걸 안 하고 있었다. 이제 부르고, 최종·접근시작 관절각을 화면에 찍는다.

## 세션 9 (이어서 2) — 대상 고르는 규칙의 약점 3가지 + Unity 관찰 경로

### 사용자 질문: "접근해야 될 대상"은 어떻게 동작하나

`arm/approach_object.py`의 `observe()` 네 줄이 전부다.

1. `is_grasp_candidate()` — **YOLO 가 찾은 것만** 후보(모양 경로는 화면에만, 2026-09-21 결정)
2. `--target cup` 을 주면 그 이름이 들어간 것만
3. `poses.sort(key=lambda p: p.position[2])` — **카메라에서 가장 가까운 것**
4. 나머지는 "같이 보인 것"으로 화면에만

실측: 종이컵 93 %(0.24 m) + 주스병 83 %(0.22 m) 중 **주스병**을 골랐다.
**확신이 높아서가 아니라 2 cm 더 가까워서다.**

약점 3가지를 BACKLOG **A-9** 로 등록했다(1등 거절 시 포기 / 대상이 흔들림 /
이미 있는 `Tracker` 를 안 씀). **이번엔 고치지 않았다** — 사용자 지시가 "문서화".

### 창 글씨 한글 깨짐 → 영어로

`arm/watch_arm.py` 의 matplotlib 창에서 한글이 전부 네모로 깨졌다
("Glyph 49552 missing from current font"). 한글 글꼴을 찾아 쓰는 방법도 만들어 봤지만
**되돌리고 창 안 글씨를 영어로 바꿨다**(사용자 지시). 이유가 더 낫다 — 글꼴에 기대면
그 글꼴이 깔린 컴퓨터에서만 제대로 보여 원칙 2에 어긋난다. 설명은 터미널에 한글로
찍히므로 읽는 데 지장 없다.

### Unity 에서 구경하기 — 배관이 이미 있었다 (다만 구멍 하나)

사용자 질문: "비전 카메라가 식별한 걸로 URSim 이 움직이는 걸 Unity 에서 볼 수 있나?"
→ **된다. 새로 만들 것이 거의 없었다.**

```
arm/approach_object.py --move  --(RTDE)-->  URSim
arm/ur_rtde_bridge.py --echo-only --(UDP 5010)--> Unity UrArmReceiver
                                                  -> UrArmTwinDriver -> 화면의 팔
```

**찾아낸 구멍**: 브리지에 **읽기 전용 모드가 없었다.** `--ip` 를 주면 항상 제어 연결까지
잡는데, ur_rtde 의 제어 경로는 로봇에 컨트롤 스크립트를 올리는 방식이라 **한 번에 하나만**
가능하다. 그래서 브리지를 띄워 두면 `approach_object.py --move` 가 붙지 못한다.

→ `--echo-only` 를 새로 만들었다: 제어 연결을 아예 안 잡고, Unity 명령 수신 포트도
바인드하지 않고(구경하러 띄운 것이 남의 통신을 끊으면 안 된다), 읽어서 보내기만 한다.

**직접 돌려서 확인함**: 브리지를 `--echo-only` 로 띄운 채 `approach_object.py --move` 를
돌렸더니 **제어 연결이 정상으로 붙었고**, Unity 포트(5010)로 22초 동안 **220개 패킷**이
갔으며 그 안에서 관절각이 **최대 100.1도** 움직였다.

🛑 **Unity 화면 자체는 확인 못 했다** — 이 컴퓨터에 유니티 에디터가 떠 있지 않다
(`unity-cli status` 전부 not responding). 씬·오브젝트·버튼 위치만 코드에서 찾아 안내했다.

- 씬: `unity/Assets/Scenes/Pipeline_Demo_GraspLift.unity` (UrArmReceiver 가 있는 유일한 씬)
- 오브젝트: `UR16e_DG5F_PicknPlaceAgent` — UrArmSender/UrArmReceiver/UrArmTwinDriver/
  PicknPlaceArmJointPanel 이 **전부 여기 한 오브젝트**에 붙어 있다
- Play 중 화면 오른쪽 "URSim 연동 방향" 에서 **`URSim→Unity`** 를 누른다(두 방향은
  상호배타 — `Unity→URSim` 과 동시에 켜면 되먹임 루프)
- Unity 안의 "브리지 실행" 버튼은 `UrArmBridgeLauncher.arguments` 기본값이
  `--ip --echo-to-unity` 라 **제어 연결을 잡는다** → 이번 용도로는 인스펙터에서
  `--ip --echo-only` 로 바꿔야 한다

## 세션 9 (이어서 3) — 관측 유효시간 2초 → 10초

사용자 지시: "2초 너무 빠르잖아 10초로 늘려."

**왜 2초가 모자랐나**: 사진을 찍고 팔이 움직이기 시작할 때까지 사이에 **사람이 승인하는
단계**가 있다(`arm/approach_object.py` 의 "이 자리로 팔을 보낼까? [y/N]"). 사람이 화면의
좌표를 읽고 판단하는 데 2초는 모자라서, **정상 절차인데도** "관측이 너무 오래됐다"로
거절됐다. 물체는 사람이 놓아둔 채 가만히 있으므로 10초 안에 움직일 일은 없다.

고친 곳: `config/rtauto_config.py` 의 `MAX_POSE_AGE_SEC` 기본값 `2.0` → `10.0`
(+ `.env.example`, 그 값을 언급하던 문서 문구 2곳). 값은 여전히 `.env` 로 덮어쓸 수 있다.

**직접 돌려서 확인함**
- 5초 뒤에 `y` 를 치는 사람을 흉내내어 `--move` 실행 → **도착 확인됨**(전에는 여기서 거절)
- 같은 조건에서 `RTAUTO_MAX_POSE_AGE_SEC=2` 로 되돌려 실행 →
  **"관측이 너무 오래됐다(3.14초 지남, 허용 2.00초)"** 로 정상 거절
  → 막는 기능 자체는 살아 있고 한계값만 늘어난 것을 확인

⚠️ 이 값이 커질수록 "그 사이 물체가 옮겨갔을 위험"도 같이 커진다. 사람이 물체를 옮기며
반복하는 시연(`--watch`)에서는 오히려 줄여야 할 수도 있다 — 실물에서 재조정할 것.

## 세션 9 (이어서 4) — 카메라 관점 보기(`--show`)

사용자 질문: "비전카메라 관점에선 어케봄"

### 먼저 확인한 것 — 창을 따로 띄우면 안 된다

`vision/d405/yolo_assist.py --live` 를 옆 터미널에 같이 띄우라고 안내하려다 **실측으로
확인**했더니 틀린 안내였다. **D405 는 한 번에 한 프로그램만 열 수 있다.** 두 번째
프로그램이 열리기는 하는데, `d405_stream.open_depth()` 가 "영상이 안 들어온다"고 보고
**카메라를 하드웨어 재설정**해 버린다 — 그러면 **먼저 뜬 쪽이 조용히 죽는다.**

그래서 보기 기능을 `arm/approach_object.py` **안에** 넣었다(`--show`).

### 무엇이 보이나

한 창에 두 장을 나란히 — 왼쪽 색 사진, 오른쪽 거리 사진.

- YOLO 가 찾은 것 전부: **주황 테두리**
- **실제로 가기로 고른 물체: 굵은 초록 테두리 + 가운데 빨간 점 + "← 이걸로 간다"**
  (여러 개가 보일 때 어느 것으로 가는지가 화면에서 바로 보여야 한다 — A-9 약점②③을
  고친 것은 아니고, 최소한 **눈으로 알아챌 수 있게** 만든 것이다)
- 왼쪽 위 글자: 고른 것·확신·거리, 카메라 기준 좌표와 크기, 같이 보인 것,
  그리고 **설 자리(로봇 기준)** 또는 거절 이유

창은 사람이 `y/N` 을 치기 **전에** 갱신된다 — 무엇을 보고 고른 자리인지 눈으로 확인한
뒤에 승인하게 하려는 것(원칙 6).

⚠️ 창 **제목**만 영어다(OpenCV 가 창 제목에 한글을 못 넣는다). 그림 **안**의 글자는
`view_d405.put_lines/put_labels` 가 PIL 로 그려서 한글이 제대로 나온다 — 이미 있던 도구다.

### 직접 돌려서 확인함

- 그림을 파일로 뽑아 눈으로 확인: 종이컵(87 %)은 주황, 주스병(75 %)은 초록 + "이걸로
  간다", 한글 전부 정상. 거리 사진에서 두 물체가 노랗게(가까움) 구분돼 보인다.
- `--look --show --watch --interval 2` 로 40초 실행 → **12바퀴, 오류 없음.**

돌리는 법:

    source vision/.vision/bin/activate
    python arm/approach_object.py --look --show                 # 카메라만, 한 장 보고 아무 키
