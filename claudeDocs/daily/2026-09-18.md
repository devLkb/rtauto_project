## 세션 1 — 잡은 뒤 물체가 얼마나 돌아가는지 재기 (기울기)

### 사용자 질문
"들어올렸을때 기울기도 0도에 가까웠으면 좋겠는데 이것도 고려해서 지금 파지 테스트중인가"

- ⚠️ **성공 판정에는 아직 안 넣는다 — 기록만 한다.** 몇 도를 넘으면 실패로 볼지는 실제

## 세션 2 — 손끝 센서 없이 "잡았다" 알아내기 (설계 + 코드)

### 사용자 요청
붙여넣은 설계 프롬프트 — 전류 + 위치 오차 + 속도로 접촉을 추정하고, 들어올려 확인하는
구조를 Python 으로 설계.

### SDK 에서 **확인한** 사실 (추측 아님)

`vision/dg5f/vendor/dgsdk-python/libs/DGDataTypes.h` 의 `ReceivedGripperData` 주석:

- `joint` = 도, `current` = **mA**, `velocity` = **rpm**, `temperature` = °C
- 즉 **세 신호가 전부 실제로 들어온다**

⚠️ **다만 지금 브리지는 속도를 안 받고 있다.** `dg5f_sdk_bridge_dgsdk.py` 의
`RECEIVED_DATA_TYPE = [1, 2, 7, ...]` 에 VELOCITY(4)가 없다 → 0 만 들어온다.

또한 `SetCurrentControlMode` / `SetTargetCurrent*` / `SetGraspData(graspForce)` 가 있어
**전류 상한을 걸고 쥐는 것**도 가능하다 — 실측 후 비교할 것.

### 만든 것

| 파일 | 하는 일 |
|---|---|
| `docs/GRASP_CONTACT_DETECTION.md` | **설계 정본** |
| `hand/grasp_contact.py` | 판단 규칙만. 하드웨어가 안 들어온다 |
| `hand/measure_baseline.py` | 무부하 전류 기준표 만들기 (`--fake` 지원) |
| `hand/grasp_sequence.py` | 순서도 (닫기 → 쥐기 → 들기 → 확인) |
| `hand/tests/test_grasp_contact.py` | **손 없이 도는 시험 17개 — 전부 통과** |
| `config/rtauto_config.py` + `.env.example` | 기준값 17개 (원칙 1) |

### 설계에서 중요한 판단 3가지

**1. "멈췄다" 만으로는 절대 안 된다.**
시킨 각도까지 **다 가서** 멈춘 관절도 속도 0, 전류 낮음이다. 이걸 접촉으로 세면 **빈손도
"잡았다" 가 된다.** 그래서 "시킨 데까지 못 갔다"(각도 오차)는 뺄 수 없는 조건이다.

**2. 전류 기준을 숫자 하나로 못 박지 않는다.**
무부하 전류는 관절마다·각도마다 다르다. `measure_baseline.py` 로 관절 20개 × 각도 10도
구간마다 평균·흔들림을 재고, 기준 = `평균 + max(흔들림×6, 80 mA)` 로 쓴다.
**기준표가 없으면 코드가 시작을 거부한다.**

**3. 확인 방법을 바꿨다 — 시험이 설계 구멍을 찾아냈다.**
처음엔 "물체가 빠지면 손가락이 더 닫힌다" 로 잡으려 했다. 그런데 닿은 관절의 목표를 그
자리에 세워 두므로 **물체가 빠져도 손가락이 0.5도밖에 안 움직인다** — 못 잡는다.
→ **집어보기**로 바꿨다: 들어올린 뒤 일부러 5도 더 조여 보고, 실제로 들어가면 빈손.
확인이 끝나면 되돌린다.

### 정직하게 — 아직 모르는 것

- 무부하 전류가 실제로 얼마인지 모른다. 잠정값이 한 자릿수 틀릴 수도 있다
- 속도(rpm)가 실제로 들어오는지 확인 못 했다 (켜야 한다는 것까지만 확인)
- 집어보기 5도가 종이컵을 찌그러뜨릴지 모른다
- `SetGraspData` 내장 파지를 안 써 봤다

**실물 검증 0회.** 스위치·랜 어댑터 도착이 선행 조건.

## 세션 4 — 학습이 안 되던 이유 두 개를 찾았다

13종 채점표(468칸, 36분)가 끝나 짝짓기 → 학습까지 돌렸다. **세 번 돌렸고, 두 가지를
고쳤다.**

### 1차 — 기준선 한참 미달

```
평균: 배운 것 57% / 안 배운 물체 54%
```

**배운 데이터조차 57%** 였다. 물체를 4종 → 13종으로 늘렸는데 그대로였다.
못 일반화한 게 아니라 **못 외운 것**이다 → 데이터 문제가 아니다.

### 고친 것 ① — 입력 숫자가 너무 작았다

모든 길이가 **미터**라 점 좌표가 0.01~0.05, 손바닥 위치가 0.03~0.05. 신경망 입장에선
거의 0을 넣는 것과 같아 안쪽 계산이 눌린다. **20배 곱하는 것으로 해결**(단위 환산일
뿐이라 정보는 안 버린다).

| | 전 | 후 |
|---|---|---|
| 배운 것 맞힘 | 57% | **79%** |
| 배운 것 F1 | 0.32 | **0.56** |
| 안 배운 물체 | 54% | 64% |

### 채점 방식이 잘못돼 있었다

좋은 자세가 14%뿐이라 **"다 나쁘다"고만 찍어도 맞힘 86%** 가 나온다. 그런데 그건
자세를 하나도 안 내놓는다 — 쓸모 0인데 점수는 1등인 잣대였다.

실제 쓰임은 맞히기가 아니라 **고르기**다(후보 36개를 매기고 1등을 쓴다). 그래서
`rank_poses()` 를 넣어 **"고른 자세가 진짜 좋았나"** 로 잰다. 비교 대상은 아무거나
찍기(1개 14% / 3개 37%).

### 2차 — 계산 규칙과 **소수점까지 같았다**

계획서 §8 의 "계산 방식보다 나은가" 를 재려고
`superdex/scripts/geometric_pose_score.py` 를 만들었다. 규칙은 두 줄:

> 점수 = (파지할 공 안에 든 점의 비율) − (파지 중심에서 물체 중심까지 거리 ÷ 반경)

손의 생김새는 **시뮬레이터에서 직접 쟀다**(짐작 아님):

```
손바닥 기준 축: z = 손가락이 뻗는 방향, x = 손바닥이 보는 쪽, y = 엄지↔새끼
벌림 폭 0.232 m / 오므렸을 때 0.089 m / 파지 중심 (0.0356, 0.0007, 0.0426)
```

| | 1등 | 3등 안 |
|---|---|---|
| 배운 것 | 15% | 62% |
| **계산 규칙(두 줄)** | **15%** | **62%** |
| 아무거나 찍기 | 14% | 37% |

**학습의 값어치가 0이었다.**

### 고친 것 ② — 구조적 결함. 이게 진짜 원인이다

계산 규칙이 **맨 먼저 하는 일**이 "점 덩어리를 손바닥 기준으로 옮기기" 다. 그게 없으면
채점 자체가 불가능하다 — "이 자세가 좋은가" 는 결국 "**내 손 기준으로** 물체가 어디
있나" 이기 때문이다.

그런데 신경망 구조가 이걸 **못 하게 돼 있었다**:

```
점 덩어리 → [모양 요약] ┐
                       ├→ 합쳐서 → 점수
자세 7개  → [자세 요약] ┘
```

**모양을 요약하는 단계에서 자세를 아직 안 봤다.** 그래서 "물체가 내 손 앞에 있나" 를
만들 방법이 아예 없다. 학습을 아무리 오래 해도 못 만드는 정보다.
계산 규칙과 점수가 같았던 건 우연이 아니라, **그 구조로 낼 수 있는 최선이 딱 그
수준**이었던 것이다.

→ 점 덩어리를 **미리 손바닥 기준으로 옮겨서** 넣도록 바꿨다. 자세 위치는 옮기기에
이미 들어가므로 따로 안 넣고, 방향 4개만 남긴다. 입력은 여전히 점 덩어리 + 자세
후보뿐이라 §7-3 은 그대로다.

**3차 학습 결과 대기 중** (`superdex/results/train_13obj_palmframe.log`).

### 채점표 자체의 결과 (이건 확정)

- 물체 13종 × 자세 36개 = **468칸**, 다 성공 194칸 / 다 실패 274칸
- **13종 전부에 통하는 자세는 36개 중 1개뿐** (앞 0.05 m, 높이 0.05 m, tilt+90)

## 세션 8 — 설정 훑기, 그리고 **조명이 성능을 좌우한다** (확인 대기)

### 사용자 지적: "RealSense Viewer 로 보면 성능이 좋은거같은데"

짐작하지 않고 **설정(visual_preset) × 해상도를 전부 훑어** 쟀다.
기준: 파지 거리(0.10~0.30 m)에서 **늘 값이 나온 화소 비율**.

| 해상도 | 설정 | 값있음 | 늘나옴 |
|---|---|---|---|
| **640×480** | **default (지금 쓰는 것)** | 57% | **86%** |
| 640×480 | custom(0번) | 57% | 85% |
| 848×480 | medium_density | 41% | 87% |
| 848×480 | default | 57% | 82% |
| 1280×720 | default | 55% | 60% |
| 640×480 | high_accuracy | 12% | 34% |

**지금 설정이 이미 제일 좋다.** 그리고 **해상도를 올리면 오히려 나빠진다**(1280×720 에서
60%) — 화소가 작아질수록 무늬 맞추기가 어렵다.

→ "Viewer 가 더 좋아 보이는" 이유는 성능이 아니라 **보기**였다:
  ① Viewer 는 색 범위를 장면에 맞춰 자동으로 늘린다. 우리는 고정해 둬서 범위 밖이
     한 색으로 눌렸다 → **기본을 자동으로 바꿨다**(`--fixed-range` 로 되돌릴 수 있다)
  ② Viewer 는 구멍 메우기가 켜져 있을 가능성이 크다 → 화면이 꽉 차 보인다.
     **그 빈 곳은 지어낸 것**이므로 우리는 계속 안 쓴다. 화면에 그 사실을 적어 뒀다

## 세션 10 — 물체 찾기에 YOLOE 를 도우미로 (브랜치 → merge)

### 왜 붙였나

사용자가 화면에서 찾은 문제 — *"큰 종이컵, 작은 종이컵이 나란히 있으면 둘을 한 물체로

사용자 제안: *"걍 기존 zed에 남아있는 사전학습된 Yolo로 식별하는건 안되냐"*

### ① ZED 모델은 **실측으로 탈락**시켰다

`vision/zed_object_detection/weights/dg5f_target_objects_yolov8s.pt`(9종)가 그대로
남아 있었다. 그런데 우리 D405 사진에서 **확신 기준을 5 % 까지 낮춰도 거의 못 찾았다** —
컵이 정중앙에 크게 있는 사진에서도 `plastic cup 10%` 가 전부였고, 대신 모니터를
laptop 으로 잡는 것만 나왔다.

원인은 두 가지를 의심해 시험했다(색 치우침 / 너무 가까움). "3배 멀리 보이게" 하면
10% → 33% 로 올랐으니 **거리 쪽 영향이 있었다.** 다만 **원인을 더 파지 않고 버렸다** —
공식 모델이 훨씬 잘하므로 파 볼 값어치가 없다.

### ② 공식 모델로 갈아탄 과정 (전부 같은 사진으로 견줬다)

| 같은 사진 | ZED 모델 | YOLO11n | YOLO11s | **YOLOE26-n** |
|---|---|---|---|---|
| 흰 컵 | 10 % | 92 % | 89 % | **89 %** |
| **캔** | 못 찾음 | **못 찾음** | **못 찾음** | **77 %** |
| 마우스 | 못 찾음 | 83 % | 91 % | **90 %** |
| 테두리 | 없음 | 있음 | 있음 | **있음** |
| CPU 한 장 | — | 41 ms | 76 ms | **43 ms** |

- **COCO 계열은 캔을 원천적으로 못 찾는다** — `can` 이라는 종류가 아예 없다
- **YOLOE 는 글자로 찾을 것을 정한다** → 정해진 종류에 안 묶여 우리 목적에 더 맞는다
- **l(큰 것)은 안 쓴다.** CPU 228 ms 로 5배 느린데 결과가 같았다.
  사용자: *"시연장엔 노트북이랑 로봇장비만 갖고갈거라 사양이 높으면 안돼"*

⚠️ **이름이 맞는지는 중요하지 않다 — 테두리가 목적이다.** 캔이 `bottle` 로 불렸지만
(77 %) 테두리는 정확했다. 우리는 점 덩어리를 잘라내려는 것이지 이름표를 붙이려는 게 아니다.

### ③ 고친 것들

- **네모 박스는 배경까지 긁어온다.** 박스 안 점을 통째로 쓰니 텀블러가
  **324×344×598 cm** 로 나왔다. → 테두리(mask) 사용 + 박스 안에서 한 번 더 나눠
  **카메라에 가장 가까운 덩어리**만 쓴다
- **242 MB 를 시연 노트북에 안 들인다.** YOLOE 는 글자를 이해하려고 별도 모델이
  필요한데 **미리 한 번만** 하면 된다. `make_ready.py` 가 구워 **11.5 MB 파일 하나**로 만든다
- `NOT_OBJECT` 에 person·책상·의자·모니터 — 잡으러 가면 안 되는 것들

### ④ 사고 두 건

- **torch 가 갈아치워졌다.** ultralytics 설치 중 2.1.1+cu121 → 2.14.0+cpu 로 바뀌어
  **CUDA 가 꺼졌다**(원칙 2 위반). 되돌리고 requirements-vision.txt 에 경고를 달았다
- **242 MB 파일이 merge 에 딸려 들어갔다.** 빼고, 아직 서버에 안 올린 상태라
  이력에서도 지웠다 — 저장소 **312 MB → 85 MB**

### ⑤ merge 직전에 시험이 버그를 잡았다

`.env` 의 카메라 실측값(fx=642.10, cx=640.69)은 **1280×720 기준**인데, 640×480 으로
물어봐도 그대로 돌려주고 있었다 — **2배 틀린 값이 조용히 나간다.** 문서에는 "해상도마다
다르다" 고 적어 놓고 코드는 안 지켰다. `D405_CALIB_WIDTH/HEIGHT` 를 두고 환산하게 고쳤다.

### 남은 진짜 문제

**흰 종이컵의 거리를 못 잰다.** YOLO 는 "여기 컵이 있다" 를 정확히 말하는데 깊이가
비어 점 덩어리를 못 만든다. 적외선 무늬를 쏘는 장치가 없어 민무늬 면을 못 재는 문제다.
조명을 밝히면 나아진다(14 % → 45 % 확인).

할 수 있는 것: ① 조명 밝히기(0원) ② **물체에 무늬 넣기**(스티커·테이프, 전시용으로
현실적) ③ 적외선 조명기 추가(하드웨어 확정이 깨지므로 안 함)

### 먼저 정정 — **적외선 무늬 장치는 D405 에 안 통한다**

무늬가 YOLO 가 보는 사진에도 찍힌다 → 켜고 끄며 두 장 찍는 구성이 필요하다.

### 사용자 결정

먼저 **코드부터 고친다**(장비 구매·재측정보다 앞에). 브랜치 `vision/sparse-depth-objects`.

### 🛑 고치려고 읽다가 **버그 두 개**를 찾았다 — 컵이 안 잡히던 이유의 큰 몫

**① 좌표계가 어긋나 있었다 (치명적).**
깊이 사진은 줄이기(decimation) 때문에 색 사진의 **절반 크기**다(640×480 → 320×240).
그런데 `split_by_boxes` 가 **깊이 화소 번호를 환산 없이** YOLO 테두리에 대고 있었다.
→ 화면 **가운데 있는 컵의 점이 테두리 밖으로 밀려나 통째로 버려진다.**

실측(합성 장면, 시험으로 재현): 화면 한가운데 컵의 점 1911개 →
**환산 없음: 물체 0개 / 환산 있음: 물체 1개(3.0×3.8 cm, 0.25 m)**

**② "이 점은 썼다" 표시가 한 건도 안 먹고 있었다.**
덩어리의 점이 원래 몇 번째 줄이었는지를 **값 비교**(`np.isin`)로 되찾고 있었는데,
float32↔float64 를 오가며 값이 미세하게 달라져 **하나도 못 찾는다.** 그래서 YOLO 가
쓴 점이 "남은 점" 으로 다시 흘러가 **모양 쪽이 같은 물체를 또 만든다.**
→ 덩어리가 **번호(index)를 들고 다니게** 고쳤다.

## 세션 13 — 자로 재서 대조. **큰 컵은 1 mm 차이, 작은 컵은 반토막이었다**

### 사용자가 자로 잰 값 vs 화면 값

| 물건 | 자로 잰 것 | 화면 값 | 판정 |
|---|---|---|---|
| 큰 컵 (89번) | 입구 지름 **8 cm**, 높이 11.5 cm, 바닥 6 cm | **8.1** x 6.1 x 6.2 cm | 입구 지름 **1 mm 차이** ✅ |
| 작은 컵 (153번) | 입구 **7 cm**, 높이 7 cm, 바닥 5.5 cm | **3.2** x 1.7 x 1.2 cm | **반토막** ❌ |

사용자 관찰: *"가까이서 봐야 좀 실제 크기에 맞게 잘 추정함"* — 맞는 관찰이고,
아래 원인과 같은 이야기다.

**⚠️ 화면의 세 숫자는 "물체의 실제 크기" 가 아니라 "카메라가 본 면의 크기" 다.**
위에서 비스듬히 내려다보므로 컵의 **높이 11.5 cm 는 애초에 안 들어온다**(입구 테두리와
윗부분만 보인다). 큰 컵의 8.1 cm 가 맞은 것은 그것이 **입구 지름**이기 때문이다.

### 🛑 작은 컵이 반토막 난 원인 — **조각 하나만 쓰고 있었다**

작은 컵은 뒤쪽에 있고 큰 컵에 반쯤 가려서 거리값이 숭숭 뚫렸다. 그러면 덩어리 묶기가
**여러 조각으로 부순다.** 그런데 코드는 그중 **카메라에 가장 가까운 한 조각**만 쓰고
있었다(`min(pieces, key=distance)`) — 그래서 3.2 cm.

같은 장면에서 `139번 [모양] 2.7x3.4x3.7 cm` 도 나왔는데, **이것도 같은 작은 컵의
나머지 조각**이다 — 한 물건이 둘로 세어지고 있었다.

### 고친 것

1. **조각을 도로 합친다** (`_merge_pieces`). YOLO 가 이미 "여기까지가 한 물체" 라고
   말해 줬으므로, 가장 가까운 조각에서 5 cm 안쪽의 조각은 전부 같은 물체로 본다.
   그보다 뒤는 배경이므로 계속 버린다(텀블러 324x344x598 cm 를 막던 장치는 살아 있다).

## 세션 14 — **한 물건이 둘로 세어지던 것**을 고친다 (확신 기준으로는 안 고쳐진다)

### 고친 것

⚠️ **추정 물체의 크기는 다시 계산하지 않는다** — 그 크기는 테두리에서 나온 값이고,

### A. 흰 컵 깊이 — 조언자가 매긴 순서

| 순위 | 방법 | 판단 |
|---|---|---|
| 1 | **좌우 원본 영상 확인 + 노출 수동 시험**(게인은 16 고정) | 가장 먼저 |
| 2 | 물체 중심으로 자동 밝기 잡기, 찍는 동안 밝기 고정, 모자라면 15 FPS | 전시 전 |

| 5 | 가시광 보조조명·무늬 투사 | 조건부 |

**우리 짐작을 두 군데 고쳤다.**

1. 🛑 **"흰색이니 밝기를 낮추면 된다" 고 단정하지 말 것.** 우리가 잰 화면 전체 밝기
   99 vs 148 은 **컵이 타서 뭉개졌는지(포화)를 말해 주지 않는다.** 컵 부분의
   **좌우 원본 영상을 따로 봐야** 갈린다. 반대로 어두울 땐 종이의 약한 무늬가
   잡음에 묻힌 것일 수도 있다 — 둘은 정반대 처방이다.
2. 🛑 **`auto_exposure_priority` 는 D405 에 해당 없다.** 이름과 달리 "어두우면
   프레임률을 떨어뜨려도 된다" 는 옵션이고, 현재 구현은 **별도 RGB 센서 경로에만
   등록**돼 D405 의 공유 센서 경로에는 없다. 장노출이 필요하면 **15 FPS 모드를 명시적으로
   비교**하는 쪽이 맞다.

덤: D405 는 **깊이 쪽 노출이 컬러에도 같이 걸린다**(별도 RGB 노출이 없다).

**가시광 무늬 투사** — 컬러를 안 더럽히는 일반 해법은 없다고 못 박았다. 같은 센서가
무늬를 보고 거리를 재므로 무늬를 지우면 거리도 사라진다. 대신 **"정지 직후 깨끗한
영상으로 테두리를 한 번 얻고, 무늬를 켠 채 거리 사진만 여러 장"** — 매 장면마다
껐다 켤 필요는 없다는 구성을 권했다.

**좌우 원본 영상**(SDK `infrared` 1·2 스트림)은 **진단용으로 가치가 크다.** 다만
매칭을 직접 다시 구현하는 것은 후순위 — 카메라 안 전용 회로를 못 이긴다는 뜻이
아니라, 무늬 없는 곳은 어차피 "주변과 매끄럽게 이어진다" 는 가정으로 메우는 것이라
**점이 촘촘해진다고 근거가 늘어나는 게 아니기 때문**이다.

**성긴 깊이로 버티는 방향은 맞다고 확인.** 다만 우리 8 cm → 8.1 cm 결과는
**"입구 폭은 잴 수 있다" 의 증거일 뿐** 중심축·전체 높이·뒤쪽 면까지 검증한 것이
아니라고 못 박았다. 권한 순서: ① 형상 모델 없이 **위치와 손 벌림 폭부터** ②
컵처럼 보이는 것에만 **원뿔대(위아래 지름이 다른 원기둥) 가정** ③ 하나로 못 정하면
**범위를 유지** ④ 모자라면 **한 번 더 정지 촬영**.

### B. 한 물건이 둘로 세어지는 것 — 진단

> **핵심: "크기 계산에 안 썼다" 와 "다른 물체의 점이다" 가 같은 뜻으로 처리된다.**

마스크로 주인을 정함 → 일부 점으로 크기 계산 → **계산에 안 쓴 점을 주인 없는 점으로
돌려보냄** → 모양 쪽이 그 점으로 새 물체를 만듦. (`yolo_assist.py:387`, `:454`)

점을 **세 상태**로 나누라고 했다: **주인 확정**(계산에 안 써도 남에게 안 넘김) /
**주인 불확실**(보류, 바로 새 물체로 세지 않음) / **주인 없음**(모양 쪽 후보).

세션 14·15 가 실패한 이유 — **방향은 맞았지만 서로 다른 문제 네 개를 한꺼번에 바꿨다.**
특히 `_absorb_halo` 의 **1.5 cm 고정 확장**이 좌표축에 나란한 상자를 모든 방향으로
키워 책상·옆 물체를 먹었을 수 있다. 경계 어긋남은 **깊이 화소 0 → 1 → 2 칸**으로
시험하는 게 맞다(화소 한 칸의 실제 폭 = 거리 ÷ 초점거리).

🛑 **"추정 물체 크기를 16 cm 로 제한해 화면에서 지우기" 는 주 해결책이 아니다.**
**"물체가 있다" 와 "손으로 잡을 수 있다" 는 별도 판정**이어야 한다.

다시 할 때의 순서(한 번에 하나씩, 매번 화면 확인):

2. 마스크 경계의 작은 어긋남만 처리(0→1→2 화소)
