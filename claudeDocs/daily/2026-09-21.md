### 1. D-10 — 노출 훑기 도구 신설 (`vision/d405/exposure_sweep.py`)

**판정: [D-10] 도구는 새로 만듦 / 실물 흰 컵 실험은 아직 안 함**(사무실 책상 위에
컵을 놓고 정식으로 스윕하는 것은 다음 세션 또는 사용자가 직접).

기능:

- 시작 전에 **이 카메라가 실제로 허용하는 노출/게인 범위를 SDK 에서 읽어 출력**한다.
  범위 밖 값을 요청하면 **조용히 자르지 않고 건너뛰며 이유를 알린다**(계획서 요구사항).
- 자동 노출을 **명시적으로 끄고, 껐는지 다시 확인**한 뒤 게인을 고정한다.
- 노출값마다: 자리 잡을 시간을 버리고 → **RAW**(다듬기 없음)와 **FILTERED**
  (`d405_stream.DepthFilters`, 기존 실시간 파이프라인과 같은 다듬기)를 **나란히** 측정.
  노출마다 `DepthFilters` 를 새로 만들어 이전 노출의 temporal 흔적이 안 섞이게 했다
  (아래 2번 항목에서 만든 지식을 바로 여기 적용한 것).
- 색 사진 + **좌우 원본(적외선) 영상**을 노출마다 저장 — "타서 뭉개졌는지"는 밝기
  숫자만으로 못 가른다는 2026-09-18 세션 18 교훈을 반영.
- ROI(관심 영역)는 `--roi x,y,w,h`(색 사진 픽셀 기준)로 단순하게 받는다. 픽셀 좌표를
  모르면 `--preview-only` 로 색 사진만 먼저 찍어 확인.
- CSV 열: `exposure_us,gain,kind(raw/filtered),frame_index,valid_depth_ratio,
  median_depth_m,depth_std_m,point_count,timestamp,object` (+ROI 열).
- 끝나면(예외가 나도 `finally` 로) **원래 자동노출/노출/게인 값을 복원**한다.

**실물로 확인함(스모크, 정식 실험 아님)**: `--exposures 2000,16000 --frames 3 --settle 5`
로 실제 카메라를 열어 끝까지 돌렸다 — 노출이 실제로 바뀌는지(`get_option` 으로
재확인), CSV 12행이 정확한 열로 남는지, `_color/_ir_left/_ir_right/_depth_raw/
_depth_filtered.png` 5종 파일이 노출마다 저장되는지, 끝나고 설정이 원복되는지
(`자동노출=True, 노출=33000, 게인=16` — 원래 기본값과 일치) 전부 확인했다. 사무실
일반 조명 장면(장면 안에 흰 컵을 놓지 않음)이라 **판정에 쓸 수 있는 실험 결과는
아니다** — 스모크 테스트 산출물은 지우고 커밋하지 않았다.

**다음 세션(또는 사용자)이 할 것**: 흰 종이컵을 카메라 앞 10~20 cm 에 고정하고
`python vision/d405/exposure_sweep.py --object paper_cup --roi <컵 픽셀좌표>` 로
정식 스윕 → CSV 와 좌우 원본 사진을 보고 A(빛 문제)/B(무늬 문제) 판정.

### 2. temporal filter — "과거 프레임을 들고 있다"를 SDK로 확인, `reset_temporal_history()` 추가

**판정: [temporal stale] SDK상 가능성 확인함 — 실물 팔 이동으로 재현하지는 못함**
(카메라를 실제로 이동시키려면 로봇팔 또는 사람이 손으로 옮겨야 하는데, 이 세션은
자동화된 터미널 작업이라 물리적으로 카메라를 옮기지 못했다 — 정직하게 남긴다).

- pyrealsense2 문서 대신 **설치된 SDK 에서 직접** 읽었다(위 표). 기본 persistency
  mode 가 3("Valid in 2/last 4")이라는 것은 **d405_stream.py 의 지금 코드가 실제로
  겪는 값**이다 — 만들 때 옵션을 하나도 안 건드리므로 기본값 그대로 쓰고 있었다.
- pyrealsense2 필터 객체(`temporal_filter`)에는 **내부 상태만 지우는 API가 없다**
  (`get_option`/`set_option`/`process` 등만 있음, `dir()` 로 직접 확인) — 그래서
  유일한 해결책은 **새 객체로 바꿔치기**하는 것이다.
- `DepthFilters.reset_temporal_history()` / `DepthStream.reset_temporal_history()`
  신설 — `self.temporal = self.rs.temporal_filter()` 로 새 객체를 만들어 끼운다.
  다른 필터(줄이기·공간 다듬기)는 안 건드린다.
- `exposure_sweep.py` 가 노출마다 `DepthFilters` 를 새로 만드는 방식으로 **바로 이
  기능을 실전에 썼다**(노출을 바꿀 때도 이전 노출의 과거 프레임이 안 섞여야 하므로
  같은 문제다).
- 시험 4개(`test_d405_stream.py`) — 카메라 없이 실제 `pyrealsense2` 필터 객체로
  reset 이 새 객체를 만드는지, 다른 필터는 안 건드리는지, `filters=None`일 때
  아무 일도 안 하는지 확인.

**남은 일**: 팔에 카메라를 달고 실제로 위치 A→B 이동시킨 뒤 reset 유무에 따라
깊이가 달라지는지 보는 것은 D-7(손목 카메라 위치 맞추기) 이후, 실물 팔이 있어야
가능하다. 지금은 **API 와 이유만 마련해 둔 상태**다.

### 3. D-9 — YOLO "소유(ownership)"와 "계측(measurement)" 분리 (중복 검출의 진짜 원인)

**판정: [D-9 중복] 코드로 재현·수정함 / 실물 컵 2~3개 나란히 놓고 재확인은 아직 안 함**
(사무실에 컵을 새로 배치하는 것은 사용자 쪽 작업).

2026-09-18 세션 18 에서 바깥 조언자가 짚은 진단 — *"크기 계산에 안 썼다"와 "다른
물체의 점이다"가 같은 뜻으로 처리된다* — 을 코드에서 실제로 확인했다.
`yolo_assist.py:split_by_boxes()` 가 `used[idx_in[o.index]] = True` 로 **계측에
실제로 쓴 점만** 소비 처리하고 있었다 — YOLO 마스크 안이지만 계측(가까운 무리
합치기)에 안 쓴 점은 "주인 없는 점"으로 되돌아가 `pts[~used]` 를 거쳐 모양(geometry)
쪽으로 넘어갔고, **같은 물체가 또 하나 생겼다.**

고친 것: `used[idx_in] = True` 로 **소유는 마스크 안 전체, 무조건, 계측 성공 여부와
무관하게** 먼저 확정한다. 계측(크기·중심 계산)은 그 아래에서 지금처럼 신뢰도 높은
subset(가까운 무리 + `ESTIMATE_BAND_M` 안쪽 병합, 부족하면 테두리 추정)을 그대로 쓴다.
**마스크 바깥 점은 그대로 `owner` 배정에서 걸러지므로 이 변경과 무관하게 계속
geometry fallback 으로 남는다.**

과거 실패했던 halo 방식(2026-09-18 세션 14, 물체 주변 1.5 cm 3D 확장 → 배경을 먹어
되돌림)은 **반복하지 않았다** — 이번 수정은 3D 공간을 확장하는 것이 아니라, 이미
마스크 안에 있다고 확정된 점의 "소유권 유지 범위"를 계측 성공 여부와 분리한 것뿐이다.

시험 3개 추가(`TestOwnership`):
- 마스크 안에 거리 차가 큰 두 무리(계측엔 가까운 무리만 쓰임) — 먼 무리가
  `rest`(geometry fallback)로 새지 않는지
- 완전히 겹치는 두 YOLO 마스크(확신 0.4/0.9) — 물체가 하나만 나오고 확신 높은 쪽이

### 4. depth stack 실시간 비교 — `--frames 1` vs `--frames 5` 실측

**판정: 실물로 직접 비교함.** 같은 자리, 같은 장면에서:

| | `--frames 1`(기존 `--live` 기본) | `--frames 5` |
|---|---|---|
| 값 있는 화소 | 69% | 69% → **81%** (+9,524개) |
| 찾은 덩어리 | 2개 | **4개** |

**여러 장 합치기가 실제로 화면에 보이는 물체 수를 바꾼다** — 2026-09-18 세션 18 이
지적한 대로, 지금까지 `--live`(1장)로 평가한 것은 이 효과를 한 번도 반영하지 못했다.

고친 것(`yolo_assist.py`): 화면·로그에 **"1장만 사용 — 값 있는 화소 X%(여러 장
합치려면 --frames 5)"** 를 `--frames` 값과 무관하게 **항상** 표시하도록 했다(전에는
`n_frames > 1`일 때만 안내가 떴다 — 1장 모드에서는 지금 몇 장을 쓰는지 화면에서 알
방법이 없었다).

### 5. eye-in-hand tracking 정책 — `Tracker.reset()` 신설

**판정: 최소 안전 정책(세션 단위 재시작) 구현함 — base-frame tracking(D-7 이후 최종
방향)은 손대지 않음.**

`Tracker` 는 카메라 기준 좌표 이동 거리로 같은 물체를 판단하는데, eye-in-hand 는
"물체는 그대로, 카메라가 움직인다" — 팔이 이동하면 카메라 기준으로는 물체가 크게
움직인 것처럼 보여 오판 위험이 있다. `docs/FESTA_PREGRASP_PLAN.md` §1 이 정한
최소 정책대로 `Tracker.reset()` 만 추가했다 — 팔 이동 시작 시 부르면 이전 추적을
끊고, 정지 후 새 관측을 "새 세션"으로 시작한다. 번호는 재사용하지 않는다(화면에서
같은 번호가 다른 물체를 가리키는 혼란 방지).

시험 3개(`TestTrackerReset`) — 정상 상태에서 번호 유지 / `reset()` 뒤 예전 위치와

### 6. 실물 페트병 실측 — D-9 수정이 실제로 효과 있는지, 그리고 안전망 설계 재검토

사용자가 실제로 D405 앞에 페트병(라벨 붙은 오렌지 주스병)을 놓고 사용자·AI 둘 다
같은 카메라로 여러 번 찍어 확인했다.

**① 첫 실측 — 소유권 분리 수정이 효과가 있어 보인다.** `yolo_assist.py --save` 로
찍으니 병이 **`YOLO:bottle 63%`로 1개만** 잡혔다. YOLO 마스크를 직접 뽑아 색 사진에
겹쳐 봤더니(`_debug_bottle_mask.png`, 커밋 안 함) 뚜껑까지 병 전체를 깔끔하게 덮고
있었다. 화면에 같이 뜬 다른 번호(2~5번, `모양`)는 3D 중심 좌표를 직접 찍어 보니
병과 **좌우로 12 cm 이상 떨어진** 마우스·케이블 등 **실제로 다른 물건**이었다 —
병의 중복이 아니었다.

**② 사용자 지적 — "밑에서 보면 하나, 위에서 보면 3개".** 위쪽 각도로 다시 찍어
봤는데 이번엔 **YOLO 가 `bottle` 자체를 못 찾았다**(`keyboard 84%, cup 79%` 만
검출) — 이유는 카메라가 마침 병이 아닌 다른 곳(사람 등)을 보고 있었기 때문으로
확인됨(사용자 확인). YOLO 가 놓치면 병 전체가 순수 "모양" 경로로 떨어지고, 그
경로는 반사되는 병 표면에서 거리값이 끊겨 여러 조각으로 쪼개질 수 있다 — 다만
이번 프레임에서 정확히 "뚜껑/몸통/허상" 패턴으로 갈라지는 것까지는 확정하지 못했다
(다른 물체들과 섞여 있어 단정하지 않음).

**③ 사용자 문제 제기 — "YOLOE 니까 안전망(모양) 없이 필터링만 늘리면 되는 거
아니냐".** 답: PROMPT_WORDS를 아무리 늘려도 **결국 미리 적어 둔 단어 목록**이라
"진짜 처음 보는(이름도 모르는) 물체"는 여전히 못 찾는다는 점을 설명 — 이건 이
프로젝트 목적(`CLAUDE.md`, 범용 파지)이 겨냥하는 문제라고 답했다.

**④ 사용자 정정 — 범위 오해가 있었다.** 사용자가 바로잡음: *"'상식적'인 범위
내에서 식별한 것들 중에서 잡는 거지 처음 보는 괴상한 걸 잡는다거나 그런 건 생각
하지 않았고, 한다 해도 페스타 이후 나중의 계획이다."* 즉 **지금(페스타까지)
목표는 "상식적인 범위" 물건을 확실히 인식하는 것**이고, **진짜 미지 형상 일반화는
페스타(2026-11-13) 이후 별도 과제**다 — `RL_POLICY_REDESIGN.md` §0 의 "이름 몰라도
파지"는 **SuperDex 파지 자세 학습 쪽 최종 방향**이지 D405 비전 인식의 지금 목표가
아니다. 이 구분을 `ai_festa_plan.md` §8-2에 정정 박스로 남겼다(다음 세션이 또
같은 오해를 하지 않도록).

**⑤ 절충안 채택 — 화면엔 둘 다, 후보엔 YOLO만.** 사용자 결정: "모양" 안전망은
화면에는 계속 보여주되, **실제로 팔을 보낼 후보 선정에는 YOLO 가 확실히 인식한
것만 신뢰한다.** 구현:

| 파일 | 무엇 |
|---|---|
| `vision/d405/segment_objects.py` | `is_grasp_candidate(obj)` 신설 — `obj.source`가 `"YOLO:"`로 시작하는지만 본다. 시험 3개(`TestGraspCandidate`) |
| `vision/d405/yolo_assist.py` | 화면·로그에 "잡으러 갈 후보(YOLO 인식) N개 / 화면 참고용(모양) M개" 표시. "모양"만으로 잡힌 물체는 번호를 **회색**으로, 줄 끝에 "⚠️ 참고용(후보 아님)" 표시 |

⚠️ 아직 이 판정을 실제로 써서 팔을 보내는 코드는 없다(D-7 전까지 관측·팔 이동이
안 엮여 있음) — 화면 표시와 판정 기준만 마련해 둔 상태.

**⑥ `PROMPT_WORDS`에 공구 6종 추가.** 사용자 요청으로 `screwdriver, wrench,
